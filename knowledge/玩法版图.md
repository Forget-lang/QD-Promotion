# 玩法版图 · 平台功能原子与组合玩法

> **定位**：这是「看待这个平台的视角层」——把能力拆成**功能原子**，用**原子 × 原子**组合出**生意打法**。解决的核心病根：过去 AI 在做内容时从「券种」视角出发（这张优惠券怎么设、这张次卡怎么设），来来回回都是优惠券、次卡的基础打法，挖不出平台真正的深层价值。
> **真源关系**：本图只做「玩法怎么组合」，**能力真源始终是 `spec/facts.json` + `spec/coupon-fields.json`**——每一条组合玩法必须能回这两张表溯源，凡表里没有的能力，不上屏、不进口播（铁律一）。官网（`quandao.lenmy.com`）只是「这个打法官网怎么演示」的**蓝本/启发源**，不是能力依据；官网越界写法进本文 §四（红线警示），只避雷、不采信。
> **开放而非清单**：玩法层**永远增补、永不封顶**。原子就这些，乘起来是几十上百种，还会随官网新增玩法持续变多。本图不当天花板，当天花板的就是「券种视角」的翻版。

---

## 〇、视角翻转（一句话）

平台真正强大的地方，不是「有 6 种券 + 3 种卡」，而是**「券/卡 × 发放方式 × 门店员工体系 × 转赠奖励 × 客户名单」组合出的一整套生意打法**。

- ❌ 旧视角（券种）：先选券种，再想「这张券怎么设」——产出必然是「优惠券/次卡基础打法」。
- ✅ 新视角（原子组合）：先看「这个行业最痛的时刻」，再问「用哪几颗原子能拼掉这个痛」——产出才是有玩法、有延伸面的攻略。

## 一、功能原子库（7 族 · 全部回 `spec/facts.json` 溯源）

> 每颗原子都是平台真实能力。数字细节（上限、档位、显隐联动）以 facts / coupon-fields 为准，本图不复述全部约束值，只标「能力名 + 玩法杠杆」。

### ① 产品族
| 原子 | 玩法杠杆 |
|---|---|
| 优惠券 6 型：代金 / 套餐 / 满减 / 折扣 / 兑换 / 随机金额（手气券） | 不同券种对应不同生意意图：兑换=凭券换指定物（体验/试吃）、满减=提客单、随机=抢手气 |
| 券包：2~10 种券打包、每种 1~5 张；领取=一键全部 / 随机一种 / 自选一种 | 「一键领」图省事、**「随机领」做抽奖盲盒、**「自选领」让人挑对自己有用的——领取方式本身就是玩法开关 |
| 次卡 3 型：通卡（不限次）/ 次卡（1~1000 次）/ 权益卡（≤30 项按序核销） | 年卡/月卡、10 次卡、护理套餐——三种「卖法」 |
| 次卡核销间隔 0~30 天（0=每天 1 次） | **锁客节奏的底层逻辑**：设 3 天=顾客每 3 天来一次，卡不睡死 |

### ② 发放族（触达方式）
| 原子 | 玩法杠杆 |
|---|---|
| 公开领取（卡片/二维码/海报/公众号） | 广撒网、门口拉新 |
| 私密发放（一对一、1~10 张、超时 5 分~永久、可写备注） | 定向给到对的人、储值回馈、消费奖励、给指定客户 |
| 定时开抢（公开券设领取开始/结束时间） | 稀缺倒计时、节日预发 |
| 活动海报（多张公开券聚合成一个活动页） | 一次活动多张券、统计浏览量 |
| 企微自动发券（加好友/进群/群发/小助理） | ⚠️ **红线隔离区**，见 §四，功能链不进候选 |

### ③ 限控族（谁领、领多少、何时领）
| 原子 | 玩法杠杆 |
|---|---|
| 每人限领总量 | 控制单客库存 |
| 领取周期（每天/周/月/年最多 N 张） | 锁频次 |
| 领取口令（固定 5 位 / 随机每 3 分钟变） | 神秘感、稀缺性、防薅 |
| 指定手机号白名单（≤500） | **定向唤醒**：只给名单里的人，自动强制填手机号 |
| 可用时段（星期 + 时间段，最多 2 段） | **闲时引流**：只补空档，不伤高峰价 |
| 每天核销限制 | 控制单客日耗 |
| 有效期（固定段 / 领当日起 N 天 / 领次日起 N 天，1~365） | 制造到期焦虑 |

### ④ 裂变复购族
| 原子 | 玩法杠杆 |
|---|---|
| 转赠（先到先得、可取消、转赠中锁核销） | 老带新的入口：顾客把券转给好友 |
| 转赠奖励（受赠人核销后，奖原转赠人一张私密券） | **裂变引擎**：带人的那位也有好处，且奖励发生在「第二个人核销之后」 |
| 核销奖励（核销后再得本券一张） | **复购锁客主开关**：刚到店就埋下下一次来的理由 |

### ⑤ 门店员工族（多店/分工体系）
| 原子 | 玩法杠杆 |
|---|---|
| 多门店管理（门店增删改、关店/正常） | 连锁/商场多店底座 |
| 适用门店（券/卡可核销的门店范围） | **一券多门店**：一张券决定能在哪些店用 |
| 发券员工 | 指定谁有权发这张券 |
| 角色权限（品牌/门店/员工三级，模块 + 操作两级） | 总部统一管、门店各自干 |
| 门店/员工发券·核销排行、顾客转赠/核销排行 | 门店 PK、员工 PK 的激励工具 |

### ⑥ 客户资产族（沉淀/唤醒）
| 原子 | 玩法杠杆 |
|---|---|
| 客户中心（名单/备注/导出/排序） | 把客流沉淀成可反复触达的名单 |
| 客户码 | 身份识别（不是会员体系） |
| 手机号采集 | 留号的唯一开关，回访/下次活动的靠山 |

## 三、组合视角（AI 怎么用原子组合出新玩法）

玩法的确是一个「查现成的」动作，而是「从痛点反向组合」的动作。做一条片定攻略时：

1. **抓痛点时刻**：这个行业老板最痛、最具体的那个时刻是什么（调研三问）。
2. **反向拼原子**：问「用哪几颗原子能拼掉这个痛」——不是先选券种。例：痛在「老客不肯带人」→ 拼「转赠 + 转赠奖励」；痛在「下午没人」→ 拼「券 + 可用时段」。
3. **组合推延伸**：拼出主玩法后，再顺着原子问「还能不能接上别的玩法」——例：异业合作负责第一次进门 → 进门后接「结账送券 / 次卡 / 老带新」（官网每条玩法页的「还可以继续这样做」区块就是这条链的现成示范）。
4. **回表咬合**：拼出的每个能力名回 `facts.json` / `coupon-fields.json` 溯源，凡表里没有、或属红线隔离区的（企微、券包公开领），就地改写成合规等价物或弃用。
5. **记进版图**：拼出的新组合若「本图没有、且已验证玩法逻辑成立」，就作为新条目回流进 §二，让版图越用越厚。

**组合判据**：只讲「这个功能是什么、怎么设」而不讲它的组合延伸面 = 不合格（回到券种视角）。

## 四、红线警示（官网越界只避雷，不采信）

> 官网是玩法蓝本，但它的「功能声明/数字/额度」属**断言层，永不采信**，只认 facts/coupon-fields。以下为踩到过的越界（台账完整版见 `outputs/archive/官网资源库落地规划.md` §3）。

| # | 官网写法 | 我方真值 | 处理 |
|---|---|---|---|
| R1 | 新客券包 FAQ「券包能门口公开领，进门体验可以公开」 | `facts.forbidden_claims[4]`：券包仅私密发放、无公开领取 | 券包一律按私密发放讲；「门口公开拉新」改用优惠券（可公开领取）表达 |
| R2 | 全站主打「永久免费」 | 红线：封面/CTA/首尾不强调免费，正文自然提及可 | 读官网时该卖点按红线处理，不随官网话术上屏 |
| R3 | 企微类玩法（加企微/进群）通篇站外生态词 | 三平台禁提微信/小程序/企业微信 | 只作「私域发券」思路远参照，功能链禁入候选 |
| R4 | 行业页 FAQ「仅新客使用 / 首次到店」 | 产品无新客识别能力 | 改「每人限领总量」，禁「限新客/首次到店」 |
| R5 | 行业页券面数字（39 体验/满199减50/198·3次等） | 断言层数字 | 仅作「示例值量级」参照，不照搬 |
