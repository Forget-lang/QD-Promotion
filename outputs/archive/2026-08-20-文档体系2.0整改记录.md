### 2. MEMORY 重新定位

从"项目状态 + 进度跟踪 + 决策记录"改为"决策便利贴"：
- 删除进度相关内容（进度靠 `outputs/gXX-XXX/` 目录实际状态判断）
- 只保留：红线速记、内容模式速记、开工索引、协作准则
- 明确"进度在哪看"：看 outputs 目录实际文件，不看 MEMORY

### 3. 屏数从"硬要求"降级为"推荐范围"

- 旧：总屏数 8-10 屏（硬性要求）
- 新：推荐屏数 8-10 屏，深度达标可上下浮动。屏数是结果不是原因，硬指标是深度（≥6 信息单元 + ≥2 层递进 + 三重绑定）

## 三、具体变更清单

### 🔴 实质矛盾修复（3 类）

1. **14 号文档定位打架**
   - 旧：README 和 12 号写"14 号 = 红线+核心模型+生产SOP+风格库 单一权威"
   - 新：改为"各管各的领域，14 号 = 红线唯一真源"
   - 涉及：docs/internal/README.md、12 号 §五

2. **dur 决定权三种表述并存**
   - 旧："设计稿定 dur（10 号/13 号分镜表）"vs"TTS 实测定（12 号/13 §2.6）"

## 六、验证方式

每轮整改后用以下方法验证：

1. **关键词扫描**：用 grep 扫旧口径关键词（如"≤2 个核心功能""4-5字/秒""小红书短视频""设计稿是最终权威"等），零命中算通过
2. **新会话通读校验**：让新 AI 按 AGENTS.md 顺序读完所有文档，报告发现的矛盾/重复/困惑。这是最有效的语义级校验
3. **红线闸门**：`node scripts/check-redlines.mjs`，video/src 层零命中

## 七、协作准则强化（本轮形成的共识）

- **改规则先找唯一源**：不要凭记忆改，先定位到那份权威文档，只改那一处
- **改完 grep 扫一遍**：确认没有其他文档复述了同一条规则
- **日常小改动不用全库扫**：只有大架构调整时才需要通读校验
- **决策当场回写**：不要攒到一天结束再总结，边讨论边落文档
- **进度不写 MEMORY**：进度靠 `outputs/` 目录实际状态判断
