# 文档架构演进 · ChatGPT 五层方案与 Qoder 对账（2026-09-01）

> 性质：咨询记录归档，**不是权威文档**，不作生产参照；待用户拍板后，结论回写 SKILL / changelog。
> 来龙去脉：用户就「文档体系怎么演进」咨询 ChatGPT，拿到一套五层能力系统方案（原文一）；
> Qoder 对照仓库现状逐条评估（原文二）。文中对仓库事实的引用以 2026-09-01 当时盘上状态为准。

---

## 一、ChatGPT 方案原文（用户提供）

核心思想：从「文档系统」改成「能力系统」，项目分五层——Truth（事实）/ Capability（能力）/ R&D（实验）/ Project（项目）/ Evidence（证据），SKILL 逐渐变成只描述「当前 AI 默认生产行为」的短流程，changelog 降级为纯历史时间线。要点摘录：

1. **诊断**：问题不是文档不够好，而是「研发中的方法、已验证的能力、生产规范、项目局部决策、历史过程」没有被设计成不同生命周期的东西。收敛之后 SKILL 又重新承担了太多东西（怎么做 + 为什么 + 失败史 + 拍板史 + 方法 + 约定 + 指标 + 案例）；changelog 同时承担「发生了什么 + 为什么改 + 用户说了什么 + 改了什么 + 验证 + 遗留」。这个结构一定会继续膨胀。
2. **Truth 层**：就是现在的 `spec/`，最稳定最成功，不要大改。原则：事实尽量只有一个源。
3. **Capability 层**（认为现在最缺）：`capabilities/{content,visual,engineering,quality}/`，每张能力卡写「能力 / 状态(validated 等) / 来源 / 解决的问题 / 当前方法 / 证据 / 适用 / 边界」，不写长篇教程。
4. **R&D 层**：`experiments/`，是和用户一起探索新方法的地方，每个实验回答：问题→谁提的想法→AI 路径→尝试→真实产物→用户评价→结果（失败/暂时有效/已验证）→下一步。
5. **Project 层**：`projects/G06/…`，每个项目只保存这个项目自己需要的；「G06 第 8 屏太挤」只改 G06，不要求 SKILL/R3/AI手册/战略简报/changelog 一起动。
6. **Evidence 层**：`evidence/{visual,content,ui,before-after,rejected}/`，保存「为什么相信某种方法有效/无效」，含反例（如 G05 九屏被整体否决）。
7. **Production Spec**：SKILL 逐渐变成「读取哪些事实→调用哪些能力→按什么顺序→调用哪些检查→输出什么」，反而变短。
8. **Feedback Router（它认为最重要）**：用户只说人话（「这张图不够细致」「像 PPT」「这个功能说得不对」），AI 自己分流为 PROJECT / CAPABILITY-GLOBAL / TRUTH / EXPERIMENT 四类之一，各自只动对应层。
9. **升级纪律**：全局规则不能靠一次拍板——案例认可→Evidence→多场景复验→Capability→Production Default；失败做法标 deprecated 而非删除。
10. **changelog 降级**：只回答「什么时候发生过什么变化」，不再回答「现在应该怎么做」。
11. **目标架构**（明确声明「不建议现在搬迁」）：顶层新增 `capabilities/ experiments/ evidence/ projects/ archive/`，其余保留。
12. **最终建议的第一步**：不做重构，先拿过去 10~20 次重要整改做「能力演进分析」——每次标注：用户发现什么问题→提了什么想法→AI 方案→共同实验→认可/否决→形成什么能力→应属哪层（项目局部/行业能力/全局能力/产品事实/实验中/已废弃），得到能力地图后再反查各文件该承载哪部分。

## 二、Qoder 对账评估（对照仓库盘上证据）

**总评**：这版比早前一版成熟——自带「不建议现在搬迁」刹车，且没再提 `templates/`（那一版与 08-29 共享模板层清零决议直接冲突）。诊断基本成立，但「新建四层目录」的药方会撞上本仓库用清零教训换来的几条纪律。

### 1. 它说的五层，仓库已有四层的实体，只是不叫这个名

| ChatGPT 层 | 仓库现状（2026-09-01） | 缺口 |
|---|---|---|
| Truth | `spec/` 四份真源，含真值表自证 | 无——它自己也说别动 |
| Production Spec | `SKILL.md` 唯一作业入口 | 无 |
| Project | `video/src/videos/g06/` + `outputs/g06-教培托管/` | 无，只是名字不同 |
| Evidence | `outputs/bench/`、`样本库/`、`archive/calibration/`、逐屏真图 | 有实物，缺「为什么信它」的一句话标注 |
| Capability | **确实没有** | 唯一真空缺：能力状态（已验证/实验中/已废弃）目前只活在 changelog 叙事里 |
| R&D | **没有独立载体** | 实验过程混在 changelog 每轮记录里 |

「新建四棵目录树」实际新增的只有约 1.5 层，其余是对已有东西换名重排——重排会打断 `check-doc-references`、`facts.json` 资产路径与 git 追溯，正是它自己第十九节承认不该做的。

### 2. 值得采纳的三个点（低成本、不动目录）

1. **反馈分流表**——整篇最值钱的一条。用户痛点「影响范围判断」正对应它。落法不是目录，而是文档里一小节：用户一句话 → AI 判「项目局部 / 全局能力 / 产品事实 / 实验」→ 各自只许动哪些文件。（注：本节结论已于 2026-08-31 先行落进 `AGENTS.md` §五「单片反馈不动全局层」。）
2. **能力升级/降级纪律**：「案例认可 ≠ 全局规则，须多场景复验」与 08-30「禁止一次拍板定配额」同构。可做成 changelog 条目两个新字段：`落层` + `状态迁移`，不用新文件。
3. **能力演进分析**：一次性练习，原料全在 changelog，做完再决定能力层要不要独立成文件——是先有地图、不是先画架构。

### 3. 必须警惕的两条冲突

- **capabilities/*.md 会成为新的语义漂移源**：能力卡若写「当前方法」，必然与 SKILL 正文复述同一方法，两份文字迟早对不齐——正是用户六大痛点之首。若将来落地，卡片只能写**状态 + 证据指针 + 边界**，方法本体单源仍在 SKILL，且纳入引用闸门扫描。
- **空目录即文档黑洞**：历史新增结构吸走维护注意力正是痛点之二。仓库对组件有「禁预建：无需求不建」纪律，应同样适用于目录——第一条实验记录写出来之前不该存在 `experiments/`。

### 4. 建议路径

第一步只做 §2.1（分流表进文档）+ §2.2（changelog 加两字段），跑一两片看是否真减少「陪跑改动」；同时或之后做 §2.3 演进分析，用结果决定能力层落不落地。**不建新目录、不搬现有文件。**若 changelog 两字段扛不住，再谈 capabilities/ 独立文件——那时它是从证据里长出来的，不是设计出来的。

### 5. 一句话对照

ChatGPT 的目标句「从用文档教 AI，变成用事实+能力+实验+证据+项目状态+自动验证共同培养 AI」方向没错；但本仓库的既有答案已经覆盖大半——**每类知识只有一个真源（AGENTS §二）+ 机器裁判（闸门）+ 单一作业入口（SKILL）**，缺的是「能力状态显式化」这一块。用增字段、立分流纪律来补，比盖四层楼便宜，且不制造新的漂移面。
