# QD-Promotion · 文档与知识架构

> 状态：2026-08-31 v1
> 目的：让 AI 在新会话中知道“什么是事实、什么是当前能力、什么在实验、什么只是当前项目、什么只是历史”。
> 本文件是架构说明，不是生产规则。

## 一、核心原则

QD-Promotion 的目标不是维护一个越来越大的知识库，而是形成一套越来越稳定的内容生产能力。

因此知识按**性质 + 成熟度 + 影响范围**组织，而不是按“谁最后修改过”组织。

## 二、六类知识

| 层 | 回答什么 | 默认位置 | AI 是否可直接当当前规则 |
|---|---|---|---|
| Truth | 产品真实是什么 | `spec/` + `../applet/` | 是，按真源取证 |
| Stable Capability | 已验证的方法是什么 | `docs/KNOWLEDGE-STATUS.md` + `SKILL.md` | 是 |
| Experiment | 正在尝试什么 | 实验记录/实验目录 | 否 |
| Project | 当前这条片/这个系列怎么做 | `outputs/gXX-行业/` 等当前项目 | 只对该项目有效 |
| Evidence | 为什么相信一个方法有效/无效 | `outputs/bench/`、认可/否决产物、实验证据 | 用来验证，不直接等于规则 |
| History | 过去发生过什么 | `outputs/archive/changelog.md` + Git | 否 |

## 三、三种影响范围

### Local

只影响一个镜头、一个视频或一个文章。默认不修改全局规范。

### Reusable

可能适用于一个行业/系列或多个项目，但需要验证后才进入稳定能力。

### Systemic

跨项目长期有效，且能够降低未来生产决策成本。只有这类变化才值得进入稳定生产层。

## 四、知识进入系统的路径

```text
用户观察 / 想法
       ↓
AI 可行性分析
       ↓
共同讨论
       ↓
实验
       ↓
真实产物
       ↓
用户判断
       ↓
┌───────────────┐
│               │
失败            有效
│               │
↓               ↓
保留实验/历史    继续验证可复用性
                    ↓
                稳定能力
                    ↓
                当前生产方法
```

不要跳过“真实产物 + 用户判断”直接把想法写成全局规则。

## 五、反馈处理算法

用户不需要指定文件。

AI 收到反馈后执行：

```text
1. 理解反馈
2. 判断是事实、内容、视觉、工程、策略还是偏好
3. 判断影响范围 Local / Reusable / Systemic
4. 找到最小必要修改点
5. 当前项目先修复并验证
6. 若值得复用，进入实验
7. 实验成熟后再升级 Stable Capability
8. 只有真正改变稳定生产能力时才更新 SKILL/稳定层
```

## 六、什么情况下会产生文档联动

### 不应联动

- 某一屏不好看；
- 某一句口播不好；
- 某个行业的载体选得不自然；
- 某个项目需要换功能组合；
- 当前素材不合适。

### 可能联动

- 产品事实发生变化；
- 同一问题在多个项目重复出现；
- 新方法被多次验证有效；
- 新方法明显优于当前方法；
- 新检查能稳定自动拦截过去反复出现的问题。

### 必须谨慎联动

任何“修改全局默认生产行为”的操作，都必须先说明：

- 原问题；
- 当前证据；
- 为什么认为可复用；
- 会影响哪些项目；
- 如何验证升级后没有退化。

## 七、每类文件应该保持多大

### `AGENTS.md`

越短越好，只负责入口、读取顺序、基本纪律。

### `SKILL.md`

只保留当前默认生产方法和必须执行的底线。不要继续累积长篇历史。

### `spec/`

机器友好的事实真源；禁止承担项目复盘和审美讨论。

### `KNOWLEDGE-STATUS.md`

只记录能力成熟度和状态，不复制完整规则。

### `EXPERIMENT-PROTOCOL.md`

描述如何实验和晋级，不记录具体实验历史。

### `PROJECT-UNDERSTANDING.md`

记录项目目标、角色、研发阶段、长期背景；不承担每次返工。

### `changelog.md`

只记录历史变化。新会话不应该通过它反推当前规范。

## 八、一个重要的设计目标

**信息只保留一份可执行源，其他地方尽量引用。**

如果同一事实需要在多个文件出现，优先考虑：

1. 改成引用；
2. 让脚本从唯一源读取；
3. 让代码成为动态真源；
4. 最后才复制文本。

这条原则优先于“所有文档看起来都完整”。

## 九、当前重构边界

本次 v1 不要求立刻搬迁所有旧目录，也不要求把所有历史重新分类。

先让新规则生效：

- 以后新增内容遵循新生命周期；
- 新反馈默认最小变更；
- 新方法默认实验；
- 稳定后才升级；
- 历史保持历史；
- 现有项目文件按实际生产需要逐步迁移。

这样可以避免再次为了“整理”而大范围破坏已经能工作的生产工程。
