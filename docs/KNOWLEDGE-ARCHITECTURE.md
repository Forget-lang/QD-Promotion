# QD-Promotion · 知识与生产架构

> 状态：2026-08-31 v1
> 定位：本文件是**架构契约**，不是生产手册、不是产品事实真源，也不是历史日志。
> 目标：让任何新会话都能判断“现在什么是真的、什么是当前默认方法、什么正在实验、什么只属于当前项目、什么只是历史”，并让用户的一次反馈只影响真正需要改变的层。

## 1. 最终目标

QD-Promotion 的最终目标是逐步形成一套能够稳定生产高质量宣传内容的 AI 内容生产系统。

理想状态：用户只提出宣传目标/方向，AI 自主完成行业选题、内容策划、视频/文章、视觉、动画、配音、字幕、平台适配和质量检查，直接产出可发布成品；用户逐渐从逐屏纠偏退到最终抽检。

当前仍处于**能力研发 / 方法收敛期**。规则、方法、样本、代码和检查机制都会继续演进。

## 2. 人机分工

### 用户

用户主要负责：

- 提出商业/宣传目标；
- 从真实视频、文章、图片中发现问题；
- 判断真实性、吸引力、商业价值、视觉质感和信息密度；
- 提出方向性想法、参考图和改善方向；
- 对实验结果拍板。

用户不需要知道应该改哪个文档、用什么技术实现、需要同步哪些文件。

### AI

AI 负责：

- 分析问题；
- 研究技术/内容可行性；
- 与用户共同制定方案；
- 实验与实现；
- 验证结果；
- 判断反馈影响范围；
- 只有在确认可复用且稳定后，才升级生产能力。

**方法通常不是单方面产生的，而是“用户观察/想法 + AI 方案 + 双方讨论 + 实验 + 用户评价”共同形成。**

## 3. 知识只有六种角色

| 角色 | 回答什么 | 权威/落点 | 新会话能否直接当默认规则 |
|---|---|---|---|
| Truth | 产品实际上是什么 | `../applet/` + `spec/` | 是，按真源取证 |
| Stable Capability | 当前已经验证的方法是什么 | `SKILL.md` + 本文件“稳定能力摘要” | 是 |
| Experiment | 正在尝试什么 | 实验记录/实验目录 | 否 |
| Project | 当前这一条片/这一系列怎么做 | 当前项目的 `PROJECT-SOURCE.md` 或现行项目文件 | 仅当前项目/系列 |
| Evidence | 为什么相信一个方法有效/无效 | 真实产物、bench、样本、实验结果 | 用于验证，不直接等于规则 |
| History | 过去发生过什么 | `outputs/archive/changelog.md` + Git | 否 |

不要因为一个文件写得详细，就提高它的权威级别。

## 4. 反馈分流：用户不用分类，AI 负责分类

用户只需要说“哪里不好/哪里不对/想做成什么样”。AI 按影响范围处理：

### Local

只影响一个镜头、一句话、一条片或一个当前文章。

**默认：只修当前项目。**

例：G06 S8 太挤；一句口播不自然；某张图太空。

### Reusable

可能适用于一个行业、系列或多个项目，但还需要实验验证。

**默认：先进入实验或项目/系列知识，不立即改变全局规则。**

例：教培行业使用报名表/作业本比抽象卡片更自然。

### Systemic

跨项目稳定有效，能持续降低未来生产成本。

**只有这类变化才应该改变稳定能力 / `SKILL.md`。**

例：经过多次验证后确认“产品展示优先使用真实 UI，而不是凭空绘制假 UI”。

### Product Truth

涉及产品功能、字段、限制、真实 UI、数字等事实。

**必须回 `spec/` 或产品源码。**

## 5. 方法成熟度

```text
用户观察 / 想法
      ↓
AI 可行性分析
      ↓
共同讨论
      ↓
实验
      ↓
真实产物
      ↓
用户评价
      ↓
┌───────────────┬────────────────┐
│ 未证实/失败    │ 有效             │
↓               ↓
保留实验/历史     继续验证可复用性
                    ↓
               Stable Capability
                    ↓
               Production Default
```

“AI 提出来”不是规则。
“做成功一次”不是规则。
“用户认可一次”只证明这一版有效。

成为默认方法需要：问题解决、真实产物证据、用户认可、可复用性，并且没有被后续实验推翻。

## 6. 证据优先于解释

遇到冲突或不确定时：

1. 产品行为 → 查源码/运行结果；
2. 产品事实与红线 → 查 `spec/`；
3. 视觉效果 → 看真实渲染图/视频与用户认可样本；
4. 当前生产方法 → 看 `SKILL.md`；
5. 正在探索的方案 → 看实验记录；
6. 历史原因 → 看 `changelog` / Git。

**历史记录不能自动覆盖当前规则；参考文档不能自动覆盖真源。**

## 7. 稳定能力应该承载“可复用方法”，而不是承载完整历史

当前已经得到较强证据支持、可作为默认生产方向的方法包括：

- 内容从“功能流水账”转向“实体店商家痛点 → 一套完整攻略”；
- 少讲功能，但与攻略真正相关的功能要讲透“怎么设 → 为什么 → 设置后谁看到什么”；
- 产品展示优先使用真实产品 UI / 产品源码证据；
- 优秀参考图用于提取做法/视觉语法，不直接复制载体与外观；
- 新视觉方向先做一屏标杆，用真实图验证后再铺片；
- 能机器验证的事实、红线、状态尽量机器验证；
- 真实成片与用户判断高于“文档全绿”。

这些方法仍允许被更好的实验替代；稳定不等于永恒。

## 8. 项目必须有明确的“当前源”

一个项目内部可以有很多输出物，但必须明确：

> **哪一个文件是当前项目的决策源，其他文件是派生物、发布物、渲染物或历史。**

以 G06 为例，当前内容/分镜决策源明确在：

`outputs/g06-教培托管/PROJECT-SOURCE.md`

该文件负责指向当前有效的项目源；历史版本不再作为新会话默认依据。

未来新项目优先采用同样的“项目源 + 派生物”结构。

## 9. 当前项目源与派生物的关系

推荐关系：

```text
项目目标 / 项目源
        ↓
内容与场景决策
        ↓
口播 / 分镜 / 发布稿 / Remotion 数据
        ↓
渲染产物
        ↓
真图/视频审核
```

当用户修改一个当前项目决策时，AI 应先修改最上游的项目源，再判断哪些派生物需要重新生成或重新审核。

不要为了“保持同步”手工复制同一段知识到多个无来源文件。

## 10. 文档边界

### `AGENTS.md`

只负责入口、读取顺序、基本纪律。越短越好。

### `SKILL.md`

只负责“当前默认如何生产”。不负责记录每次整改为什么发生。

### `spec/`

只负责机器可读事实、红线、字段、素材登记等真值。产品事实有冲突时回源码。

### `docs/KNOWLEDGE-ARCHITECTURE.md`

只负责本架构契约：知识角色、反馈分流、成熟度、项目源/派生物关系。

### `docs/PROJECT-UNDERSTANDING.md`

只负责项目目标、人机分工、关键演进背景，用于新会话恢复理解；不记录每次返工。

### `docs/AI使用手册.md`

只负责用户与 AI 如何协作；用户只提供目标、反馈和拍板，不承担知识路由。

### `outputs/archive/changelog.md`

只负责历史时间线。重要架构/规则变化可以记录，但普通项目局部返工不需要为了“形式完整”制造多份同步记录。

### 当前项目文件

只承载当前项目/系列需要的内容。项目源优先，其他产物可被重新生成。

## 11. AI 收到用户反馈后的标准动作

```text
用户反馈
  ↓
理解真实意图
  ↓
判断：事实 / 内容 / 视觉 / 工程 / 策略 / 偏好
  ↓
判断：Local / Reusable / Systemic / Product Truth
  ↓
找到最上游的必要修改点
  ↓
先修当前项目并验证
  ↓
如果值得复用：进入实验
  ↓
实验成熟后：升级 Stable Capability
  ↓
真正改变默认生产行为时：更新 SKILL / 稳定层
```

用户无需指定文件，也无需自己检查应该同步什么。

## 12. 什么时候可以结束“研发期”

不是因为文档不再修改，而是因为：

- 常见内容问题能被 AI 自己发现并避免；
- 常见视觉问题能被 AI 自己发现并改进；
- 产品事实错误基本由真源/检查拦截；
- 大部分项目反馈只影响项目源，不再引起文档雪崩；
- 新会话可以快速恢复当前稳定能力；
- 视频可以逐渐从“无声中间产物”走向一次生成完整成片。

那时才真正接近最终目标。

## 13. 本架构的反目标

为了防止重构再次变成维护负担，明确禁止：

- 为每种小问题新增一个 Markdown 文档；
- 把一次性的用户偏好写成全局规则；
- 把实验方案直接当生产标准；
- 把 changelog 当当前规范；
- 在多个文档复制同一个会变化的事实；
- 为了证明“文档很完整”而增加 AI 需要阅读的文字量。
