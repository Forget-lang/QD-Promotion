## 八、全局“排兵布阵”原则（整改前置总原则）

### 8.1 定义
**排兵布阵不是把文档逐个检查一遍，而是在任何整改计划开始前，先把整个项目当作一个完整作战系统摸透。**

必须先回答四个问题：
1. **我方有什么兵**：所有文档、spec、脚本、组件、素材、产品事实快照、视频产物、CI/Gate、历史证据、外部 APPLET 能力边界分别是什么。
2. **我方有什么军规**：哪些是硬规则、哪些是 Owner、哪些是检查器判据、哪些是人工审美/发布裁决、哪些只是历史经验；每条规则归谁管。
3. **我方有什么能力**：每个系统/文档/脚本/组件能做什么、不能做什么、可靠程度如何、是否能机械验证、是否依赖人工判断。
4. **哪里强、哪里弱、哪里重复、哪里断档**：识别能力不足、能力重叠、规则冲突、孤立资产、失效入口、未接入 Gate 的高风险区域，以及任何会形成“看似完整、实际无人负责”的空白地带。

### 8.2 作战顺序
**先侦察全局 → 再绘制战场 → 再分配兵力/Owner → 再识别强弱与缺口 → 再确定整改优先级 → 最后才允许修改。**

禁止：边发现边新增文档、边修改边重新定义 Owner、只看局部通过就判断全局完成、用一份新文档掩盖旧文档冲突。

### 8.3 全局资源盘点必须覆盖的八类
| 类别 | 必须摸清 | 结果 |
|---|---|---|
| 规则 | AGENTS / SKILL / spec / R2-R10 / R8 / redlines / 检查脚本 | 规则 Owner 图 |
| 产品事实 | APPLET live source / committed snapshot / facts / fields | 事实链与新旧差异 |
| 生产能力 | Remotion、组件、模板、动画、字体、素材、数据 | 能力矩阵 |
| 验证能力 | gate-all、各 check 脚本、CI、真实渲染、人工看片 | 验证覆盖矩阵 |
| 内容能力 | 策略、洞察、玩法、分镜、视觉决策卡 | 内容链路 |
| 历史资产 | archive、changelog、旧事务、旧失败证据 | 当前/历史隔离图 |
| 协作入口 | AGENTS、SKILL、接班材料、任务提示 | AI 阅读路径 |
| 外部依赖 | APPLET、CI 环境、路径解析、可用工具/权限 | 依赖与故障边界 |

### 8.4 能力分级
所有关键能力在整改前必须标为：
- **A：可靠**——职责清楚、Owner 唯一、输入输出明确、已有机械或真实证据。
- **B：可用但有边界**——能工作，但依赖人工、环境或存在已知限制。
- **C：薄弱**——经常误判、覆盖不足、没有稳定验证或职责模糊。
- **D：缺失**——当前没有能力或无人负责。

**C/D 不是要求立即新增系统；首先判断能否通过调整 Owner、删除重复规则、修复检查器或改善现有流程解决。只有现有能力确实无法覆盖，才允许提出新增能力。**

### 8.5 排兵布阵的核心输出
整改计划启动前必须形成一个可核对的全局态势判断：

`资源地图 + 军规地图 + Owner地图 + 能力矩阵 + 强弱/缺口图 + 依赖图 + 当前/历史边界 + 整改优先级`

并以此决定 KEEP / REWRITE / POINTER / DELETE / REPAIR / ADD。

其中 **ADD 是最后手段，不是默认动作。**

### 8.6 对未来 AI 的硬约束
任何后续整改 AI 看到“整改文档”“治理收口”“一致性修复”等任务时，**不得直接进入修改阶段**。必须先完成本节所定义的全局排兵布阵审计，并在审计结果中明确：
- 已有资源有哪些；
- 每项资源负责什么；
- 每项规则由谁拥有；
- 每种能力当前能做到什么；
- 哪些能力可靠、哪些能力有边界、哪些能力薄弱或缺失；
- 哪些地方重复、冲突、断档或历史污染；
- 修改会牵动哪些对象；
- 为什么选择修改/删除/保留，而不是继续新增。

**没有完成上述全局态势判断，不得开始大规模整改。**
