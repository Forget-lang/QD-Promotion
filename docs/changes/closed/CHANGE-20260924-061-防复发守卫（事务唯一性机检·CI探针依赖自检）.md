## 二、Goal

把两类"只能靠自觉"的环节变成机器会拦的：

1. **060 我实际踩过**：关闭提交漏删 `active/` 那份 ⇒ 同一事务两份拷贝同时落盘。两份**各自都合法**（active 那份 `VERIFYING`、closed 那份 `CLOSED`），逐份检查永远抓不到；而且本机契约闸门读文件系统不读 git 索引，"已跟踪但工作区已删"这一型本机根本看不见。
2. **044–048 与 057/058 的共同教训**：CI 的 `gates` job 缺依赖时，失败点藏在后面的断言/负向测试里，报错长得像"判据不成立"（AppleDouble 那次是计数对不上，ffmpeg 那次是 VERDICT 取不到），排查成本高。缺依赖应当**在第一步就用一行说清楚**。

## 三、新口径 New Policy

1. **一个 changeId 只能有一份落盘**：`check-change-contract` 在逐份校验之前先做唯一性检查——同一 `changeId` 出现在 `active/` 与/或 `closed/` 多于一份 ⇒ 硬失败，并指名修法（"移入 closed/ 必须同批删除 active/ 那份"）。
2. **CI 装完依赖必须自证**：`gates` job 在 `npm ci --prefix video` 之后紧跟一步探针依赖自检——`test -x video/node_modules/ffmpeg-static/ffmpeg`，缺失时以 `::error::` 打印**缺什么文件＋会造成什么后果（探针没量过）＋057 后不可被豁免**；通过则打印 ffmpeg 版本与字节数留痕。

## 十、Negative / Semantic Counterexample

**负向（两例，均跑真实检查器）**：

- `active/CHANGE-20200101-001`（状态 `VERIFYING`）＋ `closed/CHANGE-20200101-001`（状态 `CLOSED`）⇒ 硬失败并含「一个事务只能有一个状态源」。**关键在于两份单独看都合法**——这正是 060 的真实形态，逐份检查抓不到。
- `closed/` 内两份同 id（`…-001-甲.md`／`…-001-乙.md`）⇒ 硬失败并含「同一事务存在 2 份拷贝」。
- 正例对照：不同 id 的 active 与 closed 并存 ⇒ 仍 PASS（防误伤）。

**语义反例**：把守卫写成"active 与 closed 文件名必须不同"就是错的——本项目文件名带中文标题，移动时文件名本就可能变化，**身份是 `changeId` 不是文件名**；守卫必须按 `idOf()` 取号比对，否则重命名即漏检、或正常改名被误拦。
