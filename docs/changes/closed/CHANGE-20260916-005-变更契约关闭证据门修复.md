### 1.1 问题定性（写进契约，防止再次误判）

上一轮的错误**不是**「closed 应该重新套当前完整 schema」，而是「为了停止 retroactive schema 检查，把 closure evidence 也错误地一起删掉了」。

可复现证据：

- `a041754`（09-16 17:04，扩范围后、放宽前）对当时仓库跑出 `CHANGE-CONTRACT FAIL: 19 structural issue(s)`：其中 **14 项为「缺章节」**（retroactive schema 造成），仅 **5 项为「缺证据标记」**，且全部落在 `20260915-003` 一份上。→ 真正主因是 schema，不是证据。
- `49f8c37`（09-16 17:10）在同一个提交里做了两件事：① 把 12 章节 schema 与 Impact Map 检查移入 `if (state === 'active')`（**对**）；② 把 `mustPass` 五项证据校验替换为一句 `结论：CLOSED` 正则（**错**）。该提交的注释理由「不追溯套用当前 active schema」，对「章节 schema」成立，对「关闭证据」不成立——关闭证据本就是 `R8` §十 为「关闭时刻」定义的，不属于 active 阶段 schema。**理由用错了对象。**
- 后果复现：构造 `- 状态：CLOSED` + `结论：CLOSED`，但 机械检查 / 负向测试 / 语义反例 为 `PENDING`、`本次新增红：3`——当前 checker **PASS（EXIT=0，放行）**；`a041754` 版 checker **FAIL，15 项**，含 `CLOSED but missing 机械检查：PASS` 等。

本次只纠正两个层次：**历史结构兼容** 与 **当前关闭证据强制**，两者彻底分离。

## 二、Goal

修复 Change Contract 检查器在兼容历史 closed 事务时，把 CLOSED 的关闭证据门一并删掉的问题。

## 三、新口径 New Policy

1. **active 与 closed 的 schema 分离。** active 事务必须满足当前完整 Change Contract schema（12 章节 + Impact Map 无 PENDING）；closed 事务不得被反向要求补齐今天才出现的章节。
2. **历史兼容与当前关闭标准完全分离。** 历史兼容 ≠ 当前 CLOSED 标准豁免。新事务进入 closed，必须按当前 Closure Evidence Contract 验证。
3. **CLOSED 继续是证据状态，不是文字状态。** checker 离线验证 `机械检查` / `负向测试` / `语义反例` 为 PASS 级、`本次新增红` 数值为 0；**不假装能验证 GitHub 远程 run-id，也不要求 commit SHA**（允许写，但机器不校验其存在性——避免把一次门禁修复扩成证据溯源系统）。「这份证据是否真属于本次事务最终状态」明确划归**人工判据**；`template.md` §十二 与 `R8` §十 只约定证据定位的写法，不做机器强制。
4. **Real Output 不猜默认值，必须显式声明（二选一）。**
   - `applicable:` + 非空条目列表，列表内每项不得为 PENDING；
   - `not-applicable:` + 非空理由。
   - checker 只验证：声明存在、格式合法、applicable 项非 PENDING、not-applicable 理由非空。**不推断本事务「应该」需要什么证据。**
   - **强制点在 active 阶段**：active 事务必须写出合法声明（它本就要满足完整 schema），移入 `closed/` 时自然带着声明，**因此无需对历史事务做追溯要求**。closed 分支只做两件事：① `Real Output Verification` 章节必须存在；② 若章节内含声明则格式必须合法。**不要求历史事务补声明，也不靠永久 Warning 兜底。**
   - 该声明属于当前事务的正式结构（定义在 `docs/changes/template.md` §十一），不只藏在脚本里。
   - 说明：这不是新概念——现有事务已用散文表达同一语义（`真图/成片：N/A（本事务不改变成片）`、`不属于本事务 Closure 条件）`。本口径只是把既有 N/A 表述**规范化为机器可读形式**。
5. **用独立 fixture 防止闸门再次被拆除**；CHANGE-005 不得用自己证明自己（见 §九）。
6. **宽容格式，不宽容语义。** 解析须容忍 Markdown 强调标记与尾随说明，但 `PENDING` / `待验证` / `NOT VERIFIED` 等**不得**因含关键词而被判为 PASS。

## 十、Negative / Semantic Counterexample

**反例：关键词全中，但证据不成立。**

某事务把关闭证据写成：

```
- 机械检查：PASS（沿用上一事务历史运行）
- 负向测试：PASS（见历史 CI）
- 本次新增红：0 个（几乎）
```

关键词全部命中，`本次新增红` 也含 `0`。

**判定：仍然违规。** 但拦截分工必须说清，不得让机器假装能做到它做不到的事：

1. **机器能拦的**：`本次新增红` 做数值比较；`PENDING` / `待验证` / `NOT VERIFIED` / `N/A` 一律判非 PASS。本反例中三条证据值本身是合法的 `PASS`，所以**这一层拦不住它**——如实承认，不粉饰。
2. **必须人判的**：证据归属（所引运行是否属于本次事务最终状态）。`R8` §十 已把它定义为人工核对项；机器只校验字段取值与格式，**不假装能验归属**。
3. **不建不确定词黑名单**：用「几乎 / 大约」一类词表做硬判，会引入一条脆弱且容易误伤的规则，收益低于风险。

**语义结论：关键词命中 ≠ 证据成立。** 本次修复的目标是**恢复门槛并把机器边界说清**，不是把机器扩权成它做不到的验证器。
