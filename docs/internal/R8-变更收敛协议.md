# R8 · 变更收敛协议

> 目的：把“全局想法/新口径”从一次普通文档修改，升级为一次可追踪、可验证、可关闭的迁移事务，解决新旧口径并存、遗漏清理、反复确认的问题。
> 这是原理与协议层；具体口令入口仍由 `AGENTS.md` / `docs/AI使用手册.md` 指向本文件。

## 零、总原则：先统筹全局，后局部执行

> **先察全局，后定阵型；先立中军，后分兵执行；先清旧阵，后布新阵。**

全局变更不是“改几个文件”，而是对整个规则、Owner、入口、依赖与历史边界进行一次受控迁移。

因此，任何规则必须有明确落点；任何落点只能有一个 Owner；任何引用只能指向 Owner；任何替代必须清理旧阵；任何历史必须退出当前指挥链；任何全局改动必须先完成战场侦察与影响面布阵。

若在执行中发现第二 Owner、第二入口、重复规则、当前/历史混淆、新旧并存、或检查器与真实语义冲突，必须立即 STOP，回到侦察与 Owner/冲突审计，不得继续用局部补丁推进。

## 一、基本模型

一次全局变更不是“新增一条规则”，而是：

> **旧状态 → 全局侦察 → Owner/阵型确认 → 影响面布阵 → 新状态 → 迁移 → 机械验证 → 反例验证 → 真图/成片验证 → CLOSED**

任何替代型变更必须回答：

- 新口径是什么
- 被替代的旧口径是什么
- 唯一 Owner 是谁
- 当前入口是什么
- 哪些资产受影响
- 哪些旧资产保留但禁止回用
- 什么条件满足后算完成

## 二、变更前置：战场侦察与阵型确认

在写 Change Contract 的同时，AI 必须先完成最小全局排兵布阵，不得因“只是文档改动”跳过：

1. **资源地图**：规则、spec、脚本、模板、组件、输出、历史、变更事务、CI/Gate。
2. **Owner 地图**：每个被触及概念的唯一当前 Owner；非 Owner 的引用/解释位置。
3. **入口地图**：AI 入口、生产入口、状态入口、事实入口分别唯一；任何第二入口直接列为冲突。
4. **冲突/重复/断档**：同概念多处定义、旧口径残留、无 Owner 规则、历史越权、重复流程。
5. **依赖与影响面**：哪些文件、脚本、组件、模板、当前产物、CI 会被牵动。
6. **当前/历史边界**：哪些内容只作为证据，哪些内容仍属于当前指挥链。
7. **优先级**：先 P0 结构性风险，再 P1 维护风险，最后 P2 表述与整理。

这一步可以作为 AI 的内部审计结果，不要求为其额外制造长期文档；不得为了“留痕”再创建新的治理 Owner。

## 三、变更契约 Change Contract

全局变更开始前，AI 先生成一份变更契约，不先改文档。

最少包含：

- `changeId`
- `goal`
- `newPolicy`
- `owner`
- `entry`
- `replace`
- `remove`
- `preserve`
- `scope`
- `affectedAssets`
- `acceptance`

用户只需要确认契约方向；确认后进入执行阶段。

## 四、影响面 Impact Map

执行前必须扫描：

- 权威规则文档
- 真源 spec
- 检查脚本
- 模板与提示词
- 组件目录
- 当前进行中的片子
- 参考样本
- 旧口径登记
- 当前入口与状态入口

输出四态动作：

- `ADD`：新增
- `REPLACE`：替代
- `REMOVE`：删除/停用
- `PRESERVE`：保留但不可回用于新产出

**ADD 不是默认动作。** 只有现有 Owner/资源无法承载，且侦察证明新增必要时才允许 ADD。

## 五、迁移而不是叠加

替代型变更不得只新增新规则。

必须同时完成：

1. 新规则进入唯一属主
2. 旧规则进入废止登记
3. 旧规则的代码/模板/示例/提示词被清理或标记为历史保留
4. 新产出路径不得再命中旧口径
5. `check-doc-references` 与对应领域检查通过
6. 非 Owner 文档只留下指针，不保留第二份规则正文

## 六、机械收敛

机械验证用于回答：

> “旧口径是否还存在于禁止出现的位置？”

至少覆盖：

- 旧术语
- 旧数字
- 旧路径
- 旧组件名
- 旧布局名
- 旧模板名
- 旧规则片段
- 第二 Owner / 第二入口的特征

机械验证通过不等于语义完成。

## 七、语义反例

每个重要全局变更至少构造一个“故意绕开关键词但仍违反新原则”的反例。

例：

- 旧规则“不做五节点流程图”
- 错误变体：“五个状态框依次连接”
- 语义结论：仍属于旧模式，应被视觉验收拒绝

## 八、视觉/成片验证

涉及内容、视觉、动效的变更，机械检查之后必须进入真实产物验证：

- 至少一个真实关键帧或短片
- 一屏标杆先行
- 视觉判据逐项验收

“文档通过”不等于“视觉通过”。

## 九、关闭条件

变更只有在以下条件全部满足后才能标记 `CLOSED`：

- 影响面已处理
- 新口径已落唯一属主
- Owner/入口唯一性已确认
- 旧口径已清理/登记
- 非 Owner 重复规则已清理为指针
- 当前/历史边界已确认
- 机械检查通过
- 至少一个反例测试通过
- 真实产物通过对应验收
- 本次新增红为 0

**关闭是证据状态，不是文字状态。** `CLOSED` 只能写在所有关闭条件已有可核对证据之后；不得通过脚本改写 `PENDING/VERIFYING`、替换数字或复制历史 PASS 来制造关闭证据。

## 十、Closure Report

执行完成必须提交极简收敛报告：

```text
Change ID：
目标：

唯一 Owner：
唯一入口：

已修改：
已废止：
影响面：已处理 / 总数
Owner/入口冲突：PASS / FAIL
旧口径扫描：PASS / FAIL
机械检查：PASS / FAIL
负向测试：PASS / FAIL
语义反例：PASS / FAIL
真图/成片：PASS / PENDING
本次新增红：0 / N

结论：CLOSED / NOT CLOSED
```

**证据要求：**每个 `PASS` 必须对应本次事务最终状态的真实命令/CI/产物证据；报告应记录检查名称、结果、必要时的运行/提交标识。历史运行只能作为背景，不能替代最终状态证据。`PENDING` 不得在没有重新执行的情况下改成 `PASS`。

## 十一、关闭操作边界

- 先完成迁移与验证，再写 Closure Report。
- Closure Report 只能总结已经发生的证据，不负责生成证据。
- 不使用“自动把状态改绿”的关闭脚本作为验收机制。
- 推荐关闭顺序：**最终候选状态提交 → fresh CI / 必要人工验收 → 根据结果形成 Closure Report → 标记 `CLOSED` → 将已关闭事务移入 `docs/changes/closed/` → 再执行一次最终 fresh CI**。
- 关闭后的事务不得继续承担新的整改范围；新问题另建 Change ID。

## 十二、责任边界

- 用户：决定方向、确认视觉与最终发布
- 方法论/视觉负责人：设计变更契约、影响面、质量标准与验收方案
- 项目 AI：执行迁移、改文档/代码、跑检查、提交 Closure Report
- 机器检查：验证可机械判断的约束

目标不是增加用户监督，而是让系统自己证明“已经改干净”。
