# 整改作战总纲 · 排兵布阵原则

> 定位：这是整改 AI 的**前置作战原则**，不是第二套生产流程，也不是新的业务/产品规则 Owner。
> 核心要求：**先全局侦察与排兵布阵，再制定整改计划，最后才进入 Migration。**

## 0. 最高戒律：阵型先于局部

> **先察全局，后定阵型；先立中军，后分兵执行；先清旧阵，后布新阵。**
>
> 任何规则必须有明确落点；任何落点只能有一个 Owner；任何引用只能指向 Owner；任何替代必须清理旧阵；任何历史必须退出当前指挥链；任何全局改动必须先完成战场侦察和影响面布阵。
>
> 这条原则不是要求“读更多文档”，而是要求在动任何局部之前先知道：谁负责、从哪里进入、哪些是当前、哪些是历史、修改会牵动什么、哪些地方必须清旧。发现第二 Owner、第二入口、新旧并存、历史越权或规则重复时，立即停止局部修改，回到全局审计。

## 1. 什么叫“排兵布阵”

排兵布阵不是“把所有文件读一遍”，也不是“发现问题就改”。

它要求 AI 在整改前把整个战场看成一个系统，完整回答：

1. **有什么兵**：文档、spec、APPLET/Product Truth、脚本、组件、素材、视频、CI、Gate、历史证据、变更事务等资源分别是什么。
2. **有什么军规**：哪些是硬规则，哪些是领域 Owner 规则，哪些是检查器规则，哪些只是历史经验；每条规则的适用范围是什么。
3. **有什么能力**：每个资源能解决什么问题、输入/输出是什么、机械验证还是人工判断、能力边界在哪里。
4. **哪里强、哪里弱**：哪些能力已经可靠闭环，哪些能力低覆盖、易误判、只能人工确认，哪些能力根本缺失。
5. **谁管什么**：每个概念只能有一个当前 Owner；非 Owner 只能引用、解释、提供证据，不得重新定义。
6. **哪里冲突**：当前规则互相冲突、当前与历史混淆、检查器与真实语义冲突、多个入口争夺同一任务等。
7. **哪里重复**：重复文档、重复流程、重复字段定义、重复检查、重复 Change ID、重复能力；优先合并/指针/删除，不默认新增。
8. **哪里断档**：没有 Owner、没有验证、没有输入输出、没有接班路径或无法落地的规则。
9. **牵一发会动什么**：任何修改的依赖、共享组件、脚本、spec、输出物、CI 与历史证据影响面。
10. **先打哪里**：按 P0/P1/P2 排优先级，先处理结构性风险，再处理局部表述。

## 2. 四张必须先画的地图

整改开始前至少形成四张内部工作地图；地图可以由 AI 的审计结果产生，不要求为了地图新增长期文档。

### A. 资源地图
盘点入口与作业文档、Product Truth / APPLET / spec、R2/R3/R6/R7/R8/R9/R10、scripts 与 Gate、video / outputs / knowledge / archive、Change Contracts（变更事务库）、CI / artifacts / real frames。

### B. 权威与军规地图
对每个概念标记：`Owner / 引用者 / 历史证据 / 检查器 / 人工裁决`。禁止出现两个当前 Owner，也禁止把检查器自动判断直接等同于产品事实。

### C. 能力强弱矩阵
至少判断：能否自动检测、能否自动修复、能否语义验证、是否依赖真实渲染/真图、是否依赖用户最终审美、误报/漏报风险。能力评级：`A=稳定闭环 / B=可用但需抽查 / C=弱能力或高误报 / D=缺失`。

### D. 依赖与冲突地图
记录一处修改影响哪些 Owner、哪些规则互相引用、哪些脚本依赖文档命名、哪些历史材料可能污染当前入口、哪些修复会制造新重复或新入口。

## 3. 整改决策顺序

严格采用：

`侦察 → Owner → 入口 → 当前/历史边界 → 冲突 → 影响面 → 优先级 → KEEP / REWRITE / POINTER / DELETE / REPAIR → Migration → Verification → Closure`

**ADD 不是默认选项。** 只有现有 Owner/资源确实无法承载且审计证明新增必要时，才允许 ADD，并必须走 R8。

## 4. 能力低，不等于规则低

如果检查器能力弱或误报，不能为了让检查器通过而降低正确语义。

正确顺序：

`验证真实语义 → 判断检查器 → 修检查器 → 加正/负向测试 → 再验证文档`

典型反例：合法 `R10-产品事实源解析协议.md` 被旧正则误识别为 `10-...`。此时应修检查器，而不是改掉合法文件名。

## 5. 当前项目的作战编制

| 编制 | Owner / 能力 | 不得越界 |
|---|---|---|
| 总入口 | `AGENTS.md` | 不拥有领域细节 |
| 唯一生产主干 | `SKILL.md` | 不复制产品真值/历史 |
| 产品事实 | `APPLET / Product Truth / spec` | 不由视觉或历史文档代替 |
| 业务流程解释 | `R2` | 不兼任生产入口/字段真值 |
| Remotion 技术 | `R3` | 不决定镜头审美 |
| UI 视觉证据 | `R6` | 不成为产品事实真源 |
| 工程实现/组件 | `R7` | 不决定内容方向 |
| 全局变更治理 | `R8` | 不成为第二生产流程 |
| 视觉导演 | `R9` | 不拥有产品事实 |
| Product Truth 解析协议 | `R10` | 不创建第二份产品真值 |
| 历史/证据 | `archive` | 不反向指挥当前生产 |
| 检查器 | `scripts / Gate` | 不凌驾真实语义 |
| 最终审美/发布决策 | 用户 | 不由自动检查器冒充 |

## 6. 什么时候才允许“开始整改”

只有当 AI 能明确说明：资源盘点完成；Owner 唯一性明确；当前/历史边界明确；入口唯一性明确；主要冲突与重复已列出；能力强弱和误报风险已知；影响面已知；P0/P1/P2 顺序明确；没有因为“想让检查器变绿”而改变正确语义。才进入 Migration。否则继续侦察，不得凭局部结果大规模修改。

## 7. 反复出现的错误动作

- 看到缺一个说明就新增一个文档；
- 看到旧词就直接删除而不登记 deprecated alias；
- 看到检查器报错就修改正确文档；
- 把 archive 当当前规则；
- 把 UI 截图当 Product Truth；
- 把脚本 PASS 当成语义正确；
- 把局部 CI 通过当成全局闭环；
- 没有 Impact Map 就修改多个 Owner；
- 没有入口审计就新增入口；
- 用一次“大而全”的重写替代增量迁移。

## 8. 最终原则

> **行军打仗，先知敌我与地形，再排兵布阵；排兵布阵完成前，不准贸然开战。**
>
> 对本项目而言，“战场”就是整个文档、代码、资源、规则、能力与验证体系；“排兵布阵”就是建立全局认知、Owner 边界、入口唯一性、能力强弱、依赖冲突和整改优先级。整改不是改文件数量，而是让整个系统更简单、更明确、更可验证、更不容易被下一位 AI 误读。
