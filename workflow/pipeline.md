# workflow/pipeline.md · 生产流水线（流程环节 + 全部闸门）

> 最后校验：2026-08-27（文档重构阶段 2 建立；由 M1-内容策划手册 §1-§2、M2-视频制作手册 §一/§2.1-2.8/§五/§六/§七/§八、M3-平台发布手册 §1/§7/§8.2-8.4、素材索引表·登记流程/找图指引 迁移合并）
> **定位**：这是「怎么做」的流水线——策划 → 视频 → 发布三个环节，外加贯穿的资产流程。每个环节的步骤、闸门、自检清单都就地放在对应步骤下，执行时对照即可。
> **真源指向**：产品事实/数字/能力边界 → `spec/facts.json`；红线/合规口径 → `spec/redlines.json`；素材登记 → `spec/assets.json`；操作步骤/状态流转 → `docs/internal/R2-业务流程.md`；Remotion 技术原理/组件 API → `docs/internal/R3-Remotion技术参考.md`；审美与视觉原则 → `workflow/craft.md`；玩法/卖点/客群/句式/干货 → `workflow/策划弹药库.md`；封面/CTA/平台细则/标题话题 → `workflow/发布弹药库.md`。
> **不负责**：玩法/卖点/句式等「内容弹药」本身（查策划弹药库）；封面版式/话题库等「发布弹药」本身（查发布弹药库）；审美标准本身（查 craft.md）。本文件只管「按什么顺序做、每步查什么、闸门怎么过」。

## 0. 总览

### 0.1 全流程图（顺序不可乱）

```
【策划】行业选型 → 行业调研 → 玩法选择 → 文案/口播 → 干货提取 → 质量自检
   ↓ 产出「内容输入包」（业态画像/玩法方案/四件套文案/口播稿/封面文案包）
【视频】设计稿（人确认）→ 视觉预演闸门 → 阶段一画面验证（逐屏关键帧，人确认）→ 阶段二有声版（TTS/字幕/渲染/盲听）
   ↓ 产出成片 + 封面
【发布】三平台分工 → 配封面 → 写 CTA → 平台自查 → 渠道合规复查 → 发布后运营
   ↓
【回顾】生产回顾 → 沉淀经验（回写对应文档/数据文件）
```

### 0.2 三个贯穿全程的铁律

1. **事实铁律**：任何对外文案中的功能描述、数字、术语，必须能在 `spec/facts.json` 中找到依据。找不到就不写，或者标「待确认」交人核实。
2. **红线铁律**：任何对外内容，先对照 `spec/redlines.json` 的相关规则自查，再定稿。
3. **流程铁律**：写教程类内容、讲操作步骤时，回查 `docs/internal/R2-业务流程.md` 核对步骤和状态流转，不能自己编操作路径。

### 0.3 拿不准怎么办（通用规则）

- 拿不准算不算编数据 → 不写具体数字，只写"后台都看得见"
- 拿不准某个功能有没有 → 查 `spec/facts.json` 的 `forbidden_claims`（能力边界），列在里面的 = 不能写
- 拿不准某个词能不能用 → 查 `spec/redlines.json` 对应规则，没写的灰色地带，宁可不做也不踩线
- 拿不准某个字段怎么配 → 标「待确认」，交人核实，不硬写

### 0.4 用户与 AI 的边界

用户不需要阅读、记忆或维护任何文档（本文件与 spec/、docs/internal/ 都是 AI 内部实现）。用户只做三件事：**给方向/说感觉、审设计稿与关键帧、看成片**。AI 不得向用户抛文档细节或让用户做文档层选择题。

## 1. 策划（怎么想内容）

> 「内容策划」就是把"这条内容讲什么"想清楚。拆成步骤 0-4（含 3.5），每一步都有明确输入、动作、输出和闸门。闸门没通过，不许进入下一步。
> 策划产出「内容输入包」，转交给视频环节（出片）与发布环节（图文/文章）。
> 玩法库、卖点库、客群定位、句式金句、业务干货等「弹药」查 `workflow/策划弹药库.md`。

### 1.0 使用顺序：两种入口，按 0 → 1 → 2 → 3 → 3.5 → 4 执行

**入口 A（用户指定行业）**：用户说"做美业/洗车…"→ 跳过步骤 0，直接步骤 1。
**入口 B（用户说"按工作流执行"）**：AI 先走**步骤 0 · 行业选型**（AI 根据时令/节日/经营周期自主选行业，输出简报并直接开工），再走步骤 1-4。

| 顺序 | 步骤 | 做什么 | 产出 |
|---|---|---|---|
| 0 | 行业选型 | （入口 B 必走）五维判断选行业：时令/节日/经营周期/玩法匹配/差异化 | 行业选型简报（候选 Top3 + 选定 + 窗口期） |
| 1 | 行业调研 | 细分业态 + 调研三问 + 功能边界核对 | 业态画像 |
| 2 | 玩法选择 | 选 1 主 + 1 辅 + 场景策略 + 风格轮换 | 玩法方案 |
| 3 | 文案/口播写作 | 券组合 + 四件套 + 口播稿 | 内容输入包 |
| 3.5 | 干货内容提取 | 从 01-券组合文案提取可截图/可照做的具体内容，按呈现类型分类 | 设计稿画面素材清单 |
| 4 | 质量标准自检 | 6 信息单元打勾 + 深度 4 问 + 同质化检查 | 通过的内容输入包 |

步骤 0-4 走完（含步骤 3.5 干货提取）才算完成策划。

### 步骤 0 · 行业选型（入口 B 必走；用户指定行业则跳过）

> 目的：用户说"按工作流执行"时，AI 根据当前环境（季节/节日/经营周期）自主判断哪个行业最值得做宣传，并直接开工。用户不需要指定行业、不需要了解时令。

**输入**：
- 当前日期（`date` 命令获取，算季节与近 60 天节日）
- 玩法库 P-01~P-07 + 业态×玩法矩阵（见 `workflow/策划弹药库.md` §玩法）
- 近期已产出行业（`ls outputs/gXX-*` 查，避免重复）

**判断五维度**（缺一不可）：

| 维度 | 问什么 | 示例（8 月底） |
|---|---|---|
| ① 时令 | 当前季节哪些行业旺季/转折？ | 夏末秋初：茶饮仍是旺季尾巴；火锅/美容养生开始回暖 |
| ② 节日节点 | 近 2-4 周有哪些节日/节点？关联哪些行业？ | 9 月开学季 → 教育培训；教师节 → 文具/书店类（弱关联则跳过） |
| ③ 经营周期 | 该行业此刻的活动需求强弱？ | 旺季要锁客防流失；淡季要保命拉新；新店季要开业引流 |
| ④ 玩法匹配 | 能否从玩法库找到强匹配玩法？ | 用业态×玩法矩阵核对，匹配度低则换候选 |
| ⑤ 差异化 | 是否与近期已产出行业重复？ | 上条做了茶饮咖啡 → 本轮避开 |

**时令-行业参考表**（AI 判断用，非穷举，按实际日期推导）：

| 时段 | 高潜力行业（示例） |
|---|---|
| 春季 3-5 月 | 健身（3 月健身季）、美容养生、洗车（春雨后）、餐饮新菜季 |
| 夏季 6-8 月 | 茶饮、冰淇淋、游泳健身、洗车（雨季）、美发 |
| 秋季 9-11 月 | 火锅（9 月起回暖）、美容养生、教育培训（开学季）、洗车 |
| 冬季 12-2 月 | 火锅、洗浴、美发美甲（春节前）、餐饮年夜饭、美容养生 |

节日映射：情人节→美甲美睫｜妇女节→美容养生｜母亲节→美业｜开学季/教师节→教育培训｜国庆→餐饮｜双 11→零售｜春节→美发美甲/餐饮/洗浴

**动作**：
1. 运行 `date` 取当前日期 → 确定季节 + 列出近 60 天节日/节点
2. 按五维生成**候选行业 Top 3**（每个附：时令依据 / 节日依据 / 玩法匹配 / 差异化判断）
3. 选定 1 个：理由最充分 + 差异化达标（与近期产出行业不同）
4. 输出**行业选型简报**（候选 Top3 + 选定理由 + 宣传窗口期 2-4 周）→ 一句话告知用户选定结果与理由 → **直接开工步骤 1**（用户可随时喊停换行业）

**闸门**：
- 简报必须给出可验证的"时令/节日依据"（禁止拍脑袋选行业）
- 选定行业与近期已产出行业不同（差异化）
- 从玩法库能找到 ≥1 个强匹配玩法（匹配度不足则换候选）

**验证闭环**：生产回顾时记录选型命中情况（选定行业在窗口期是否确实有热度/需求），沉淀为待验证假设。

### 步骤 1 · 行业调研（三问）

**输入**：
- 行业名（可能很宽，如"美业""餐饮"）
- `spec/facts.json`（features 功能清单 / glossary 术语表 / forbidden_claims 能力边界）
- `docs/internal/R2-业务流程.md`（操作步骤/状态流转）
- `workflow/策划弹药库.md` §玩法（玩法库、业态×玩法矩阵）

**动作**：

1. **细分业态**：不要把大行业当业态。
   - ❌ 错："美业""餐饮"这种大行业，痛点太泛，写出来全是空话
   - ✅ 对："美容院""美甲美睫""头疗养生馆""茶饮咖啡"这种细分业态
   - 原则：业态越具体，痛点越精准，内容越有说服力

2. **调研三问**（三个问题都要做，缺一不可）：
   - 一问：这个业态的老板最头疼什么？→ 搜索该细分业态的经营痛点，越细越好，落到"某个时刻/某个场景"
   - 二问：这个业态现在怎么做营销？→ 搜索现有做法，找到"反常识"的切入点（比如"别人都在推销办卡，我们讲送卡"）
   - 三问：选的玩法能不能解决这个痛点？→ 结合前两问，从玩法库粗筛候选玩法，判断是否真的适配
   - 信息来源建议：行业论坛/贴吧店主抱怨、点评类平台差评、行业报告、店主访谈记录。注意：搜到的是"行业普遍现象"，不是"某个具体店的真实数据"，行文用行业泛称

3. **核对功能边界**：调研中打算用的每个功能点，去 `spec/facts.json` 的 `forbidden_claims`（能力边界）和 `features`（功能清单）核对"产品到底有没有这个能力、对外怎么说"。
   - ❌ 错：想写"顾客扫商家码核销" → 能力边界写明核销方向是商家扫顾客的码 → 必须改说法
   - ❌ 错：想写"短信验证码领券" → 能力边界写明只有手机号格式校验 → 必须改说法
   - ✅ 对：先查 facts 再动笔，写出来的每个功能都有出处

4. **判断是否重复**：查已产出的行业单元（outputs/gXX-行业/ 目录），避免重复做同一业态。已做过的业态 → 换细分业态或换主打玩法。

**输出**：
- 业态画像（100-200 字）：业态是什么、谁在开店、老板最头疼什么、现在怎么做营销
- 候选玩法清单（从玩法库初筛 2-3 个，正式确认在步骤 2）

**闸门**（全过才进步骤 2）：
- [ ] 业态是细分业态，不是大行业
- [ ] 调研三问都答了，痛点描述具体到"某个时刻/某个场景"
- [ ] 提到的所有功能都能在 `spec/facts.json` 找到依据，无一编造
- [ ] 业态画像写满 100-200 字，没有空话

**对/错例子**：
- ✅ 对（业态画像）："开在社区周边的独立美容院，3-5 个员工，主营面部护理和身体项目。老板最头疼两件事：一是办卡被顾客抵触，一提办卡不少顾客就打退堂鼓；二是好不容易办了卡，顾客也不来，卡睡死。现在营销方式是朋友圈发图加店员口头推销，效果越来越差。"
- ❌ 错："美业老板需要拓客锁客，我们的产品可以帮他们。"（没有细分业态、没有具体痛点、像广告词）

**拿不准怎么办**：找不到该业态的具体痛点 → 缩小范围继续搜，或用"场景示例+行业泛称"代替真实案例（见策划弹药库 §客群·冷启动约束），禁止编一个具体店名和数据。

### 步骤 2 · 玩法选择（1 主 + 1 辅 + 场景策略）

**输入**：
- 步骤 1 的业态画像
- `workflow/策划弹药库.md` §玩法（玩法库 P-01~P-07、业态×玩法矩阵）
- 已产出视频清单（已注册场景序列跑 `node scripts/list-assets.mjs` 查）

**动作**：

1. **查矩阵定主辅**：按业态×玩法矩阵，选该业态的 1 个主打玩法 + 1 个辅助玩法。
   - 主打玩法：视频核心内容（8-10 屏，讲深讲透）
   - 辅助玩法：视频进阶部分（1-2 屏，体现深度）；小红书图文/搜狐长文可展开
   - 矩阵里没有的业态：按"痛点是否被玩法核心思路命中"判断，从玩法库自己选 1 主 + 1 辅

2. **写一句话核心理念**：把主玩法翻译成"该业态老板能听懂的一句话"。
   - ✅ 对（美容院 + P-01）："别卖卡了，做完项目送一张六次养护卡，核销间隔设三天，顾客每三天来一次，还能转赠闺蜜老带新。"
   - ❌ 错："用次卡锁客，提升复购。"（概念，不是一句话方案）

3. **设计场景策略**（内容深度闸门第一关）：不是"次卡可以锁客"这种泛泛之谈，而是一个有细节、有逻辑的完整方案，必须含三要素：
   - 具体业态场景（如"美容院做完疗程后的送卡时刻"）
   - 核心玩法和卡券组合（如"养护六次卡 + 核销间隔三天 + 转赠闺蜜"）
   - 预期效果和逻辑链条（如"顾客每三天来一次 → 耗卡节奏锁住 → 卡不睡死 → 转赠带新客"）

4. **风格轮换检查**：与上一条已产出视频对比：
   - 风格五维至少 3 个维度不同：配色 / 动画性格 / 转场 / 字体性格 / 钩子型（五维定义见本文 §2.2 风格配置五维）
   - 叙事结构（场景序列）与已有行业视频至少 3 个位置不同
   - 禁止"换个行业词、结构照搬"（含开头句式：如 G03"火锅店老板都懂"→ 下条不得写"XX老板都懂"；开头优先用场景带入）

5. **深度预演**：按本文 §1.6 内容深度闸门，把 6 个信息单元（钩子/痛点/思路/步骤/为什么/进阶）预填一遍。填不满 → 回步骤 2 换玩法或调场景。

**输出**：玩法方案 = 主打玩法 + 辅助玩法 + 一句话核心理念 + 场景策略（含三重绑定：场景/操作/目的）。

**闸门**（全过才进步骤 3）：
- [ ] 1 主 + 1 辅都选好，辅助玩法在视频里有明确位置（进阶 1-2 屏）
- [ ] 场景策略含"具体场景 + 卡券组合 + 逻辑链条"三要素
- [ ] 每个功能点都满足三重绑定（在哪用/怎么用/用了有啥用，见 §1.6 方向锚二）
- [ ] 与上一条视频 ≥3 维不同，场景序列 ≥3 位置不同
- [ ] 6 个信息单元预演能填满（填不满 = 深度不够）

**对/错例子**：
- ✅ 对（场景策略）："美容院做完面部护理后，店员一边说'姐今天护理做得不错，送您一张六次养护卡'，一边把卡私密发放到顾客手机（操作）。卡设定核销间隔三天，顾客每三天就得来一趟（场景），三个月耗完一张卡，到店 6 次，每次都是增项销售机会（目的）。用不完还能转赠闺蜜，闺蜜到店就是新客。"
- ❌ 错："用次卡锁客，提升复购。"（没有场景、没有操作细节、没有逻辑链条）

**拿不准怎么办**：玩法不适配 → 换矩阵里的辅助玩法做主打；两个玩法都不适配 → 回步骤 1 重新细分业态。

### 步骤 3 · 文案/口播写作（券组合 + 四件套 + 口播）

**输入**：
- 步骤 2 确认的场景策略
- `spec/facts.json`（constraints 关键数值约束 / glossary 术语表 / forbidden_claims 能力边界）
- `workflow/策划弹药库.md` §卖点（10 大特色卖点 + 4 形态营销差异）、§句式（高转化句式/痛点金句）

**动作**：

1. **设计券组合 + 边界校验**：基于场景策略设计卡券组合（优惠券/券包/次卡），逐字段对照 `spec/facts.json` 的 `constraints`（关键数值约束）与 `forbidden_claims`（能力边界）：
   - 次卡走"私密发放"（次卡不支持公开领取）
   - 随机金额券金额取 1~99 的整数
   - 套餐券只写文字预约说明，不暗示"在线预约"
   - 券包/次卡不支持公开领取，只有优惠券支持公开领取
   - 其他字段（名称/面额/库存/有效期/使用条件/核销方式）以 facts 为准
   - 拿不准的字段 → 标「待确认」，交人核实，不硬写

2. **写四件套文案（G 类）**：
   - ① 活动设计总览：活动名称、目标客群、核心玩法、活动周期、预期效果（表格 + 简要说明）
   - ② 卡券制作单：每张券的逐字段配置（名称/面额/库存/有效期/使用条件/核销方式），附边界校验结果（逐券一个表格）
   - ③ 发放组合与执行顺序：发券顺序、发放渠道、话术要点、时间节点（时间轴 + 执行清单）
   - ④ 攻略长文：场景化功能教学（不是功能罗列），≥6 信息单元 + ≥2 层递进，遵守本文 §1.6 质量标准（长文格式，含小标题分段）
   - 封面文案包随四件套一同产出（抖音/小红书/搜狐三平台封面文案；封面规范见 `workflow/发布弹药库.md` §封面），不计入四件套数量

3. **写口播稿（视频用）**：
   - 按屏写：8-10 屏，每屏一段口播，对应一个信息单元
   - 字数校准：**字数/时长是内容深度的结果，不是目标**——禁止为凑参考区间硬塞冗余句
     - 完整性闸门（硬性，内容讲透为准）：≥6 信息单元 + 深度 4 问 + 干货字段展示（见步骤 3.5）
     - 时长参考（非硬性，按玩法复杂度自然落位）：简单玩法 60-90s / 标准玩法 90-120s / 复杂链路玩法 120-150s（约 660-900 字）；硬上限 200 秒
     - 无水分验证：剪掉一半会损失重要信息 = 长度合理；不损失 = 有水，精简
     - 语速验算：总字数 ÷ 预估秒数 ≤ 6 字/秒（配合 ffmpeg atempo 略快档，参数与实测见本文 §2.5 阶段二）
   - 数字写中文：口播和字幕里"3 天"写成"三天"，"198 元"写成"一百九十八元"（TTS 读中文数字更自然，且是成片硬规则）
   - **顾客反应不得绝对化**：描述顾客行为/心理/行业现象时，禁用"一……就……""都""全部"等全称断言，用"很多/不少/往往/容易"收口；产品功能与操作步骤不受此限（可确定表述）
     - ✅ 对："一提办卡，不少顾客就打退堂鼓"
     - ❌ 错："一推卡，顾客扭头就走"（绝对化——不是所有顾客都这样；且隐含"是老板把顾客赶跑的"指责感，让老板产生抵触）
     - ❌ 错："顾客一听'办卡'就警惕"（全称断言）→ 对："很多顾客一听'办卡'就警惕"
   - 每屏口播语义完整，字幕断句每行 10-20 字的要求由视频环节执行
   - 口播稿示例（美容院 P-01 钩子+痛点，约 70 字 ≈ 14 秒）："美容院还在推销办卡？很多顾客一听'办卡'就警惕。一提办卡，不少顾客就打退堂鼓；不推又没收入；顾客不是讨厌卡，是怕被套住。换个思路，别卖卡了，送。"（注意"14 秒"写成"十四秒"也一样遵守数字写中文）

4. **卖点与金句取材**：
   - 从策划弹药库 §卖点「10 大特色卖点」选 1-2 个支撑本玩法（卖点要和场景绑，不许罗列）
   - 从策划弹药库 §句式·痛点金句库 选或改痛点金句做钩子（如 J-007"卖了卡就不来了，不来就没钱赚"）
   - 从策划弹药库 §句式·高转化句式库 取句式

5. **红线与能力边界自查**（写完快速过一遍，完整规则见 `spec/redlines.json`）：
   - 三平台绝口不提微信/小程序/搜一搜（redlines `platform_diversion`）
   - 不编功能、不编案例、不编数据；案例一律用"场景示例"+行业泛称（redlines `false_claims`）
   - "最/第一/顶级/100%"等极限词禁用（redlines `superlatives`）
   - 企微用功能泛称"加好友/进群自动发券"，不直说"企业微信"（redlines `wording.wecom`）
   - 高频能力边界：不说"在线支付/买单/购券"（产品不做交易，券免费发放）、不说"会员体系/积分"（只有客户码）、不说"审核/待审核"、不说"核销活码/动态码"（详见 `spec/facts.json` `forbidden_claims`）

**输出**：内容输入包 =
- ① 活动设计总览
- ② 卡券制作单（含边界校验结果）
- ③ 发放组合与执行顺序
- ④ 攻略长文
- ⑤ 口播稿（含每屏字数预估与总字数验算）
- ⑥ 封面文案包（输入到发布环节）

**闸门**（全过才进步骤 4）：
- [ ] 券组合逐字段过完边界校验，"待确认"字段已单独列出
- [ ] 四件套 4 件齐全，攻略长文 ≥6 信息单元
- [ ] 口播语速验算 ≤6 字/秒（总字数 ÷ 预估秒数）；内容完整（≥6 信息单元 + 干货字段展示）；时长 ≤200s；不硬凑字数（字数/时长是内容深度的结果，不是目标）
- [ ] 口播/文案中所有数字都是中文写法
- [ ] 所有数字、术语都能在 `spec/facts.json` 找到依据
- [ ] 红线自查零命中（拿不准的对照 `spec/redlines.json` 对应规则）

**对/错例子**：
- ✅ 对："做完护理，送您一张六次养护卡，三天来一次，三个月正好用完。用不完也没关系，可以转赠给闺蜜。"
- ❌ 错一："充值 3000 元送 500 元"（产品不做在线支付/充值，能力边界禁止）
- ❌ 错二："扫码领券，3 天有效"（数字要写中文："三天"）

**拿不准怎么办**：数字对不上 → 回 `spec/facts.json` `constraints` 查；查不到 → 不写数字，标「待确认」。

> **→ 设计稿素材提示**：步骤 3 产出的券组合（卡券名称/面额/有效期/限领/使用须知）、发放方式、操作要点等具体内容，可作为下游设计稿的画面素材，丰富视频信息密度。设计稿会根据视频叙事需要选取，不要求全部展示。

### 步骤 3.5 · 干货内容提取（设计稿素材准备）

> 目的：把步骤 3 产出的 01-券组合文案中，**可截图、可照做**的具体内容提前梳理出来，供下游设计稿直接选用。解决"视频只讲概念不展内容"的问题。
> 本步骤是丰富画面信息密度的**途径之一**，不是硬性要求每屏堆内容。设计稿根据叙事需要灵活选取，钩子/痛点/CTA 等抽象屏不需要具体内容。

**输入**：步骤 3 的券组合与四件套文案（01-券组合文案）。

**动作**：

从 01-券组合文案中，提取所有**商家可截图保留、照着做**的具体内容，按呈现类型分类：

| 呈现类型 | 含义 | 来源举例 |
|---|---|---|
| **卡券模板屏** | 完整券面信息（名称/类型/面额/有效期/限领/使用须知） | 01 的"卡券制作单" |
| **参数清单屏** | 多张券的参数对比或配置要点 | 01 的"发放组合" |
| **流程链路屏** | 完整操作链路图（谁→做什么→结果） | 01 的"玩法链路图" |
| **操作清单屏** | 执行步骤（先做什么→再做什么→最后做什么） | 01 的"执行步骤" |
| **发放指引屏** | 发放方式 + 引导话术 | 01 的"发放渠道" |
| **对比/数据屏** | 传统方式 vs 新方式对比，或数据面板 | 01 的"活动设计总览"中的对比说明 |

**产出**：在设计稿分镜表的「画面展示内容」字段中，标注每屏具体展示的文字内容（从上述分类中选取），不是抽象描述。

**原则**：
- 画面展示 ≠ 口播念出来——使用须知 4 条直接贴在画面上，口播只讲重点（"面额 20 块，30 天有效，开启转赠"）
- 具体内容必须来自 01-券组合文案——不能凭空编，设计稿展示的每张券的参数必须与 01 一致（`spec/facts.json` 的纪律依然有效）
- 不是所有屏都要展示具体内容——钩子屏、痛点屏、CTA 屏天然适合抽象视觉（大字/对比/品牌），不需要硬塞参数

### 步骤 4 · 质量标准自检

**输入**：步骤 3 的全部产出、本文 §1.6 内容深度闸门。

**动作**：

1. **6 信息单元打勾**：按 §1.6 信息单元表逐项核对（钩子/痛点深挖/核心思路/具体步骤/为什么有用/进阶延伸）。缺一项 = 不合格，回炉。

2. **深度 4 问自检**：
   - 钩子够不够狠？前 3 秒能不能让目标老板停下来？
   - 痛点够不够深？说了"为什么会这样、带来什么后果"吗？
   - 方案够不够具体？能直接抄作业吗？
   - 有没有"哦，还能这样"的感觉？

3. **深度判断法**：试着把内容压缩成一句话。
   - 能压成"XX 行业用次卡锁客"一句话 → 深度不够，回炉
   - 要 3 句话才说得清（如"XX 行业的老板别卖卡了，改成送卡，做完项目一对一发，核销间隔设三天锁住节奏，还能转赠闺蜜老带新"）→ 深度够了

4. **同质化检查**：与已有视频对比，风格五维 ≥3 维不同、场景序列 ≥3 位置不同（步骤 2 做过，此处复核最终文案没跑偏）。

5. **内容形式匹配**：按产出类型核对信息单元数（见 §1.6 不同内容形式的深度要求）：抖音主视频 ≥6 / 小红书图文 ≥5 / 搜狐长文 ≥8 / 辅助玩法短视频 ≥4。

6. **红线复扫（最终确认）**：再对照 `spec/redlines.json` 快速过一遍数字、极限词、平台特有规则。

**输出**：自检记录（6 单元打勾表 + 深度 4 问答案 + 同质化对比表）+ 通过的内容输入包（转交视频/发布环节）。

**闸门**（全过才算策划完成）：
- [ ] 6 信息单元全勾
- [ ] 深度 4 问全过
- [ ] 一句话压缩测试：无法压成一句话（3 句话以上才说得清）
- [ ] 同质化对比表：≥3 维不同、场景序列 ≥3 位置不同
- [ ] 对应内容形式的单元数达标
- [ ] 红线零命中

### 1.6 内容深度闸门（质量标准 + 方向锚 + 自检清单）

> 策划的质量标准来自内容质量三层标准：硬边界（`spec/redlines.json` 管"会不会死"）→ 方向锚（本节管"好不好看"）→ 创作自由（§5 管"怎么达到，AI 自己说了算"）。
> 四个方向锚的完整阐述（内容定位/三重绑定/说服力/节奏）已迁入 `workflow/craft.md` §内容方向锚；本节保留闸门化的量化要求与自检清单。

#### 1.6.1 一条合格视频必须满足

| 指标 | 最低要求 | 说明 |
|---|---|---|
| **有效信息单元** | ≥ 6 个 | 见 1.6.2 列表 |
| **递进层数** | ≥ 2 层 | 痛点要有深挖、方案要有层次，不是平铺直叙 |
| **讲清怎么做** | ✅ 必须 | 具体步骤，不是"有这个功能" |
| **讲清为什么有用** | ✅ 必须 | 底层逻辑，不是"效果很好" |

**"递进层数 ≥2 层"怎么理解**：同一个点至少挖两层。
- 痛点两层：第一层"顾客办了卡不来"；第二层"为什么不来——卡睡死半年用不完，店员也没理由联系顾客"。只讲第一层 = 只有 1 层，不合格
- 方案两层：第一层"送卡替代卖卡"；第二层"核销间隔三天把到店变成节奏，转赠把老客变成发券员"。方案有层次，不是平铺直叙

#### 1.6.2 6 个标准信息单元（每条视频至少覆盖）

1. **钩子**——反常识问题 / 扎心痛点 / 数字冲击（1 屏）
2. **痛点深挖**——不止说"有这个问题"，还要说"为什么会这样"或"问题带来什么后果"（1-2 屏）
3. **核心思路**——一句话说清新方法/新角度（1 屏）
4. **具体步骤**——第一步做什么、第二步做什么，有操作路径（1-2 屏）
5. **为什么有用**——底层逻辑，让老板信服（1 屏）
6. **进阶/延伸**——一个额外的价值点，体现深度（1 屏）

\+ CTA（品牌署名，不算信息单元）

**推荐屏数**：8-10 屏（深度达标前提下可上下浮动，屏数是结果不是原因）
**参考时长**：60-150 秒（按玩法复杂度自然落位：简单 60-90s / 标准 90-120s / 复杂 120-150s；硬上限 200s）

#### 1.6.3 内容深度自检（4 条全过才算合格）

- [ ] **钩子够不够狠**：前 3 秒能不能让目标老板停下来？是反常识/扎心/数字冲击，还是平平无奇的"今天给大家介绍..."？
- [ ] **痛点够不够深**：是只说了"有这个问题"，还是说了"为什么会这样、带来什么后果、老板感同身受"？
- [ ] **方案够不够具体**：是"用次卡锁客"这种概念，还是"做完项目送一张六次养护卡，核销间隔设三天，顾客每三天来一次"这种能直接抄作业的？
- [ ] **有没有"哦，还能这样"的感觉**：看完有没有一个让人意外/眼前一亮的点？还是全是意料之中的常识？

**判断方法**：如果一条视频的内容能压缩成"XX 行业用次卡锁客"一句话，说明深度不够。如果要花 3 句话才能说清（"XX 行业的老板别卖卡了，改成送卡，做完项目一对一发，核销间隔设三天锁住节奏，还能转赠闺蜜老带新"），说明深度够了。

#### 1.6.4 不同内容形式的深度要求

| 形式 | 信息单元 | 时长参考 | 说明 |
|---|---|---|---|
| 抖音主视频 | ≥ 6 个 | 60-150s（按玩法复杂度自然落位） | 主打内容，必须讲深讲透 |
| 小红书图文 | ≥ 5 个 | — | 9 张图，图 2-图 8 都是信息单元 |
| 搜狐长文 | ≥ 8 个 | — | 深度文章，每个部分展开讲 |
| 短视频辅助玩法 | ≥ 4 个 | 60-90s | 比如单独讲"老带新怎么玩"的短内容 |

### 1.7 策划自检清单（步骤 4 使用，全部打勾才算过）

- [ ] 内容定位：看完老板会觉得"这个我店里也能用"，不是"哦有这个东西"
- [ ] 三重绑定：每个功能都讲清"在哪用、怎么用、用了有啥用"
- [ ] 说服力：每个"好"都有具体操作/数据支撑，没有口号
- [ ] 节奏：剪掉一半会损失重要信息（没水）
- [ ] ≥6 有效信息单元（按 1.6.2 打勾）
- [ ] ≥2 层递进（痛点有深挖、方案有层次）
- [ ] 讲清了怎么做（具体步骤）
- [ ] 讲清了为什么有用（底层逻辑）
- [ ] 深度 4 问全过（1.6.3）
- [ ] 一句话压缩测试：3 句话以上才说得清（1.6.3 判断方法）
- [ ] 同质化：风格五维 ≥3 维不同、场景序列 ≥3 位置不同
- [ ] 对应内容形式的单元数达标（1.6.4）
- [ ] 红线零命中（对照 `spec/redlines.json`）
- [ ] **踩坑预检（产出前强制）**：对照本文各环节规则逐条过——绝对化/凑字数硬塞（步骤 3）、开头句式模板（步骤 2）、编造功能（产品事实核对）、禁词（红线闸门）、发布稿非成品（§3.4）；画面类坑见 `workflow/craft.md` §踩坑与避坑。产出时附预检结果
- [ ] **用户视角三问**：① 我是目标老板，这段值不值得截图/照着做？② 像同行分享还是像广告？③ 信息是重要维度还是凑数？——三问全过才算合格（不只是"符合文档规则"）
- [ ] **产品事实核对（强制）**：涉及产品功能/数据/字段的表述，产出前已查 `spec/facts.json`（不凭印象；教训：编造"转赠数"统计、使用说明理解错）

## 2. 视频（怎么出片）

> 完成内容策划（拿到内容输入包）后，按本节独立完成视频制作：设计稿 → 代码 → 画面验证（逐屏关键帧）→ TTS → 成片。
> 技术"为什么"与组件 API 查 `docs/internal/R3-Remotion技术参考.md`；画风审美查 `workflow/craft.md`。

### 2.0 制作流程总览（顺序不可乱）

```
策划完成（行业/玩法/文案已定）
  ↓
① 设计稿（帧级分镜 + 口播全文 + 素材清单）→ 人确认内容方向/风格/深度 → 视觉预演闸门（§2.4）
  ↓
② 阶段一 · 画面验证：代码执行（dur 用预估）→ tsc + still 验证 → 出逐屏关键帧单张 → 人确认画面（不渲染无声版）
  ↓
③ 阶段二 · 有声版：TTS 逐屏生成 → loudnorm → ffprobe 量时长 → 算 dur 回填 → 字幕精确同步 → 渲染成片 → 盲听校验
  ↓
④ 交付：视频文件 + 生产回顾（沉淀经验）
```

**核心原则**：先确认画面再加语音，避免画面返工浪费 TTS 额度。画面确认用**逐屏关键帧单张**（每屏峰值帧 still，静态可验证布局/对比度/干货呈现），不渲染无声版视频（省渲染时间；动态转场/动画由共享组件保证）。TTS 一次生成、零调试；**语速控制用 ffmpeg atempo（见 §2.5 阶段二；seed-tts-2.0 的 speed_ratio 参数实测无效）**。

### 2.4 视觉预演闸门（设计稿后、编码前必跑）

> 目的：把"逐屏关键帧才发现风格雷同/呈现未落地"的问题**前置到设计稿阶段**（教训：5 维全不同但骨架雷同，直到无声版关键帧才暴露）。

**流程**：
1. 设计稿完成后，用**占位数据**渲染 2-3 帧核心屏 still（S1 钩子 + 1 个内容屏如 S3/S4 + 1 个收尾屏）
2. 对照检查：
   - ☐ 视觉方向与上一条视频**观感不同**（§2.2 视觉观感比对：骨架不是"白卡+图标+文字"同款）
   - ☐ 设计稿声明的呈现类型**真正可见**（如券面组件展示出券面结构，不是回落成通用卡片）
   - ☐ 前景对比度 OK（背景图与文字/卡片不撞色）
   - ☐ **可截图抄作业**：内容屏暂停截图，画面必须是一张独立的干货卡——完整参数/操作步骤/对比逻辑都在这一屏里，观众不看视频也能照着做；达不到 = 信息密度不达标，返工
3. 通过 → 交编码 agent 全量编码；不通过 → 回设计稿重做核心屏（换呈现类型/换视觉结构）

**占位数据规则**：用假字段验证视觉结构即可，不要求真实文案；验证后占位数据不进入正式数据文件。

### 2.5 两阶段生产流程

#### 阶段一 · 画面验证（关键帧确认，不渲染无声版）

> 画面确认用**逐屏关键帧单张**（每屏峰值帧 still），不再渲染无声版 mp4——静态画面足以验证布局/对比度/干货呈现，省渲染时间；动态转场/动画由共享组件保证。无声版渲染彻底取消，阶段二直接出有声成片。

1. 新建 `data/gXX.ts`：dur 用设计稿预估值（按 5.5-6 字/秒估算）；视觉 = 代码 UI + 字体 + 图标；首帧复用封面 hero 视觉
2. **字幕占位**：字幕内容按口播全文拆分（语义断句，每行 10-20 字），时间轴按预估 dur 均匀分布（仅作位置参考）

   **断句示例**：
   ```
   口播原文：开咖啡店的老板，别再让顾客充卡了。充一次几百块，顾客怕跑路不敢办；就算办了，充完就不见人，卡睡死半年用不完。换个思路——十杯次卡，锁客反而更牢。
   拆为 4 行（每行 10-20 字）：
   行1：开咖啡店的老板，别再让顾客充卡了。
   行2：充一次几百块，顾客怕跑路不敢办
   行3：就算办了，充完就不见人，卡睡死半年用不完
   行4：换个思路——十杯次卡，锁客反而更牢
   ```
3. 代码验证：`npx tsc --noEmit` 零错误 → `npx remotion still` 渲染每屏峰值帧（每屏 ≥1 帧，选屏中段：起始帧 + dur×FPS×0.3）
4. **关键帧评审**：逐屏峰值帧单张输出（gXX-s1.png ~ sN.png）→ 对照 §2.2 视觉观感比对（vs 上一条视频骨架不雷同）→ 首帧单独审（抖音首帧即门面）
5. **闸门**：人确认画面质量。不合格 → 走「指屏反馈闭环」（§2.6）→ 重渲染该屏 still；合格 → 进入阶段二

#### 阶段二 · 有声版（最终成片）

**TTS 语速实测验证（结论定稿：speed_ratio 无效，用 atempo）**：
> ❌ **已废弃做法（不要执行）**：用 seed-tts-2.0 的 `speed_ratio` 参数提速并盲听选值。实测暴露该参数**完全无效**（0.5~2.0 时长不变）。新视频**不做 speed_ratio 验证、不记录 speed_ratio 值**。
> ✅ **现行做法**：语速一律用 **ffmpeg atempo** 达成（命令见下方步骤 1）。选定流程：常速合成 → 按"口播总字数 ÷ 实测总时长"算当前字/秒 → 对照目标 5.5-6 字/秒选 atempo≈1.15~1.2 → 变速后重算 dur/字幕。**G04 实测 atempo=1.2 达 5.88 字/秒（达标）**，后续视频直接沿用 1.2，不再重复验证；若选用其他值，回写本节与 R3「音频预处理」。
> **拿不准怎么办**：先算字/秒再决定——常速合成已达 5.5-6 字/秒就不变速，宁慢勿切。

**声画字幕同步（重要环节，语速变化后尤其要注意）**：
> 语速提升后，每屏语音时长变短、dur 重新计算、字幕停留时间相应调整。工作流不变（画面验证先行 → 看关键帧 → 确认后再语音合成），但有声版必须严格执行：字幕 = 口播全文 + 标点断句 + 渲染前逐句核对（见步骤 5）。语音、字幕、画面切换三者必须保持同步——以渲染结果为准，不信预览器。

1. **TTS 语音（J-cut 一次到位）**：豆包 `seed-tts-2.0`；逐屏合成 `public/audio/{视频ID}/s1.wav`~`sN.wav`（N=屏数，按视频 ID 分子目录）；**数字统一写中文**；如有问题整体重录，不做片段微调。**语速控制**：seed-tts-2.0 的 `speed_ratio` 参数实测**完全无效**，语速一律用 **ffmpeg atempo 变速**达成：`ffmpeg -i in.wav -filter:a "atempo=1.2" out.wav`（纯变速不变调，音质无损）；目标语速 5.5-6 字/秒 → atempo≈1.15~1.2（按"口播总字数 ÷ 实测总时长"算当前字/秒后选定）；变速后 dur/字幕时间轴按新时长重算
2. **响度归一化**：`scripts/process-audio.sh`（仅 loudnorm，零裁剪零淡入）
3. **精确时长**：ffprobe / `getAudioDurationInSeconds` 测每段语音时长
4. **算 dur（确定性公式，零经验值）**：
   ```
   dur = ceilTo01(audioDuration) + extraHold
   voiceOffset = 0（画面一出来就说话；CTA 屏可 0.5s 品牌先出）
   extraHold：信息屏（hook/pain/solution/flow/grid）= 0s；数据屏（panel）= 0.8s；CTA 屏 = 1.5s
   voiceDur = audioDuration 实测值回填（音频淡出起点 = 语音实际结束帧，尾字零削波；未回填时退回到最后 12 帧淡出）
   ```
5. **字幕精确同步**：
   - 字幕内容 = **口播全文**，不做摘要不缩写——禁止沿用画面验证阶段的占位字幕，有声版必须按口播全文重写
   - **每行 = 一个语义短句**：以标点断句（逗号/句号/破折号/分号），一行不塞两个分句（行内无停顿，字数-时长相关性才准）
   - 每行 10-20 字；时间轴 = 行字数占比 × 语音实测帧数（TTS sentence 无时间戳，断句粒度误差 ±0.3s 内可接受）
   - **渲染前逐句核对**：把口播全文与字幕并排比对，口播每个分句都必须在字幕中找到（防漏字）；发现遗漏必须补全再渲染
6. **成片渲染**：`npx tsc --noEmit` → `npx remotion render`（含音频+字幕）
7. **盲听校验**：渲染后盲听全片一遍（不看画面）——检查每屏首字清晰完整、转场无爆音/尾字被切、整体节奏自然。**以渲染结果为准，不信预览器**

### 2.6 指屏反馈闭环（画面修改标准流程）

> 用户的表达方式：不干预 AI 自主设计、不要求懂术语，**不满意的表达 = "第 X 屏不好" + 参考图（可选）**。AI 承担全部理解、重设计、渲染工作。

**默认态（零干预）**：设计稿阶段 AI 用布局模式库（craft.md §布局模式库）+ 视觉参数（craft.md §视觉层级参数）自主设计，**不需要用户提供参考图、不需要用户干预**。参考图是用户的"表达工具"（替代专业术语），用户主动给才算，不是流程强制环节。

**闭环步骤**（用户指出不满后 AI 执行）：

1. **定位**：用户指出的那一屏（只改这一屏，不动其他屏；除非用户明确要求整体重做）
2. **理解**：
   - 用户说了感受（如"这屏很乱""太空了"）→ 按 craft.md §用户反馈翻译表翻译成专业指令
   - 用户给了参考图 → 按 craft.md §参考图拆解模板拆解 7 项
   - 两者都有 → 翻译 + 拆解交叉印证
3. **重设计**（该屏）：换布局模式（craft.md §布局模式库，与相邻屏不重复）/ 重排视觉参数（字号阶梯/间距/留白/色彩）/ 重设焦点（一屏一焦点）
4. **验证**：渲染该屏 still → 用户确认 → 通过才继续；不通过重复 1-3（每轮只改该屏）
5. **沉淀**：修改中发现的规律回写对应文档——新感受 → craft.md 反馈翻译表；新手法 → craft.md 参照库/布局模式库；新坑 → craft.md 踩坑与避坑

**纪律**：
- 用户没说"整体重做"前，禁止推倒重来——只改指定屏，保证其他已确认屏不受影响
- AI 必须把"用户感受"翻译成可执行指令后动手，禁止直接"把字体放大/卡片放大"式表面修改
- 每轮修改渲染 1-2 帧 still 即可，不必全片重渲（除非改的是全片氛围层等全局项）

### 2.7 视频闸门汇总（合规 / 美感 / 质检）

#### 2.7.1 合规自查（7 项必查，依据 `spec/redlines.json`）

- ☐ 无极限词（最/第一/顶级/独家/唯一）
- ☐ 无微信/小程序/搜索提及
- ☐ 无虚构功能/案例/数据
- ☐ 数字以 `spec/facts.json` 关键数值为准
- ☐ 「核销活码」不在宣传中使用
- ☐ CTA 自然收尾，无「关注/收藏/进主页」
- ☐ 「免费」未在封面/开头/结尾作为卖点强调（正文自然提及没问题）

#### 2.7.2 美感自查（逐屏对照 `workflow/craft.md` §视觉审美标准）

- ☐ V-R01 标题醒目：字号 ≥56px，颜色与背景强对比
- ☐ V-R02 内容填满上 2/3：标题+主体集中，上下不空
- ☐ V-R03 一屏一焦点：有且只有一个主视觉焦点
- ☐ V-R04 文字对比度 ≥4.5:1
- ☐ V-R05 相邻屏不重复：连续两屏布局模式不同
- ☐ V-R06 安全区：top ≥120px / bottom ≥160px / left&right ≥80px（抖音发布后左右会被遮挡，安全区按实测收紧）
- ☐ V-R07 无全屏遮罩：背景图直接透出（blur: 0）
- ☐ V-R08 信息点 ≥3：每屏至少 3 个有效信息点
- ☐ V-R09 内容屏有干货：方案/流程/优势等内容屏展示了具体、可操作的信息（如卡券参数、操作要点等），不只是抽象标题+一句话描述（具体内容从 01-券组合文案提取，设计稿按叙事需要选取）

红线全过后，建议项（V-S01~V-S14）由 AI 自主判断。

#### 2.7.3 画面验证检查（阶段一，逐屏关键帧逐项自检）

| 检查项 | 检查方法 | 通过标准 |
|---|---|---|
| 画面安全区 | 检查每屏关键帧：顶部 120px/底部 160px/左右 80px 是否有内容溢出 | 无溢出 |
| 核心内容集中 | 每屏核心内容是否在 y:200-1100 | 无内容分散到全屏 |
| 排版节奏 | 逐屏看 padding/间距/标题与内容关系 | 呼吸感好，不挤不散 |
| 整体节奏 | 按预估语速默读口播一遍 | 不拖沓不仓促 |
| 字幕位置 | 字幕在 y:1760-1920，底部距底 ≥60px | 不侵入内容区 |
| 视觉观感比对 | 逐屏关键帧 vs 上一条视频逐屏比骨架（§2.2） | 内容屏 ≥2 屏呈现类型不同，不雷同 |

| 用户视角三问 | 自问：① 我是老板这屏值不值得截图？② 干货是重要维度还是凑数？③ 与上一条观感雷同吗？ | 三问全过（不只是"符合视觉参数"） |
| 产品事实核对 | 画面涉及产品功能/统计维度/字段 → 产出前查 `spec/facts.json` | 无编造 |

> 注：转场流畅性不再单独检查（TransitionSeries 共享组件已验证；成片渲染时如发现转场问题再修）。

## 3. 发布（怎么发）

> AI 完成内容策划与视频/图文制作之后，按本节独立完成「发布前准备」：三平台规则、封面设计需求、CTA 口径、发布自查。
> 封面版式/配色/找图方法、CTA 细则、各平台规则、标题公式与话题库等「发布弹药」查 `workflow/发布弹药库.md`；本节管分工总览、转化路径、发布闸门与运营。

> 适用：三平台发布——抖音（短视频）、小红书（图文笔记）、搜狐（长文攻略）。微信生态承接位（视频号）不作为宣传发布阵地。

### 3.1 三平台分工总览（平台 × 内容形态 × 画幅 × 角色）

| 平台 | 内容形态 | 画幅 | 角色定位 | 发布关键动作 |
|---|---|---|---|---|
| 抖音 | 短视频（唯一短视频主阵地） | 9:16（1080×1920） | 算法推荐主流量池；实体店老板人群体量大，玩法型视频适配度高 | 做钩子/软种草；发布时手动设封面并关闭「自动同步首帧」 |
| 小红书 | 图文笔记（不发视频） | 封面 3:4（原图 9:16 裁切中间区） | 开店/创业人群集中；图文笔记适合深度讲解玩法 | 封面决定打开率，关键信息放中间安全区；标题/标签布局关键词 |
| 搜狐 | 长文攻略（图文文章，不带视频） | 头图 16:9（1920×1080） | 搜索端内容沉淀、利于收录；长文适合把玩法讲透 | 每篇必配 16:9 头图；SEO 关键词布局 |
| 视频号 | 仅品牌承接位 | — | 微信生态品牌承接位（可露小程序码） | 不发布宣传视频；仅作品牌承接位使用 |

- 冷启动原则：资源有限，**先做透 2~3 个渠道，不要全渠道铺开**。当前只做透抖音/小红书/搜狐三个主阵地，不铺开。
- 每周固定产出节奏（阶段二）：抖音 1~2 条视频 + 小红书 1~2 篇图文笔记 + 搜狐 1 篇长文，按选题库轮换。
- 小红书封面与抖音视频封面共用同一 hero 视觉语言（背景/主视觉/标题一致），不同载体不割裂；搜狐头图同理。

### 3.2 统一转化路径

> 三平台发布后整体跑这条链路：

```
曝光（文章/视频/海报/地推）
   → 兴趣（场景痛点 + 玩法展示）
   → 行动：扫码进入「券到卡包」
   → 商户中心「制作卡券」→ 授权创建商户
   → 第一张券制作完成（关键激活点）
   → 首次发放与核销（价值验证）
   → 留存：客户中心/统计/自动发券能力逐步解锁使用
```

- 三平台上的「行动」环节，导流仅限账号资料位（主页简介/置顶评论/私信自动回复），见发布弹药库 §CTA。
- 线下物料（台卡/海报/传单）可直接放「券到卡包」小程序码，由顾客微信扫码进入。

选题「奶茶店次卡锁客」：

- 抖音：9:16 短视频，前 3 秒钩子「90% 的奶茶店，第一张券就做错了」，末 3 秒画面停留品牌名「券到卡包」；配 C-04 卡片干货型封面。
- 小红书：图文笔记，标题「奶茶店怎么锁住回头客」（≤20 字含关键词），封面 3:4 裁切中间区，正文分点讲次卡玩法，标签 #茶饮 #门店经营 #电子券。
- 搜狐：长文攻略，标题「奶茶店锁客攻略：电子券怎么发才有效」，16:9 头图，小标题分节，SEO 埋「奶茶店 锁客 次卡」。

### 3.4 发布稿交付标准（publish md）

> 文章发布稿 = **可直接复制的成品**（`.md` 文件），不是策略描述、不是视频口播文字版。产出规范：
> **格式要求**：交付 **Markdown（.md）**，不用 .txt——txt 复制到小红书/搜狐编辑器会丢失加粗/标题/列表等格式；.md 在编辑器粘贴后格式保留。

**小红书 publish md 格式**：
```
【标题】≤20 字含搜索关键词
【正文】口语化、分行分段（痛点→干货→价值），结合小程序操作内容（字段怎么设/为什么）
【标签】#行业词 #场景词（6-10 个）
【配图说明 · 9 张图】逐张标注：图N（类型：封面设计图/截图/尾图）｜用途｜截图素材/xxx.png（发布前裁剪微信元素）
```

**搜狐 publish md 格式**：
- 完整长文（小标题分节，SEO 关键词埋入；**字数以内容讲清楚为准，不硬凑**——深度结果论，与策划步骤 3 字数校准同原则：内容完整性是硬性（搜狐长文 ≥8 信息单元，本文 §1.6.4），字数不是；无水分验证=删掉一半会损失重要信息才算写足）
- 正文内嵌配图标注：`【配图：截图素材/xxx.png】` + 图注一行 + （发布前请裁剪微信元素）
- 结构建议：开头场景 → 为什么 → 怎么做（含字段设置干货）→ 操作步骤 → 进阶玩法 → 效果数据 → 适合什么店/注意事项 → 结尾品牌署名

**通用要求**：
- **文章要丰富**：结合小程序操作内容（制券字段怎么设、为什么这么设、三步操作流程、核销/数据），不是口播文字版；深度对标行业攻略文（信息密度以内容讲清楚为准，不硬凑字数）
- **配图文件名必须与截图速查表一致**（`spec/assets.json` D 级），发布前裁剪微信元素（`spec/redlines.json` video_visual）
- 红线全过（无极限词/无微信小程序提及/不编数据/行业泛称）

#### 3.5.2 渠道风险与合规自查

> 通用红线/合规唯一真源：`spec/redlines.json`。本节仅列渠道执行层面的特有风险。

- **内部表述不得外泄**：内部文档为内部执行文档，其中的评估性表述（如「转化率高」「天然适合」）**不得直接摘抄进对外物料**；
- **地推话术**：地推人员话术以 `spec/facts.json` 为准，不得口头承诺产品外功能；
- **同质化风险**：多行业视频须做差异化（配色/视觉风/钩子），避免被判定"模板化 AI 流水账"压流量（见本文 §2.2 相似度检查）；
- **配图风险**：小红书/搜狐文内功能示意可用截图，但发布前必须裁剪掉微信元素（`spec/redlines.json` video_visual）。

**自查清单**：
- □ 对外物料未摘抄内部评估性表述（如「转化率高」「天然适合」）
- □ 地推话术与 `spec/facts.json` 一致，未口头承诺产品外功能
- □ 多行业视频配色/视觉风/钩子已做差异化（防同质化）
- □ 截图类配图已裁剪微信元素

## 4. 资产流程（贯穿环节）

### 4.1 本地素材优先检索（设计稿前置步骤）

> **素材登记唯一真源：`spec/assets.json`**（入库=登记，不登记不算入库）。AI 设计稿需要素材时先查 assets.json，不扫描素材目录本身。

素材库清单（`promotion/` 下，与 docs/ 同级；登记以 `spec/assets.json` 为准）：

| 库 | 根路径 | 内容 | 适用场景 | 引入 video/public 路径 |
|---|---|---|---|---|
| 背景素材 | `背景素材/` | 抽象模板（暖/冷色系）+ 小红书风格 | 全屏氛围背景 | `video/public/backgrounds/gXX/` |
| 图鱼纹理 | `图标素材/图鱼素材/` | 771 个纹理图案（数字命名） | UI 卡片底纹、装饰层 | `video/public/textures/gXX/` |
| 插图库 | `插图库/` | 挂件贴纸/物体插画（按类型/行业分子目录） | 情境插画 | `video/public/illustrations/gXX/` |
| 商用字体 | `商用字体/` | 普惠体/得意黑/方圆体（已 bundle 6 个） | 全片排版 | 已在 `video/public/fonts/` |

**检索流程**：
1. 判断该屏是否纯 UI 组件可表达（当前多数场景不需要外部图）
2. 需要背景图：AI 输出需求引导（风格/色调/构图），人从 `背景素材/` 子目录选；本地无合适 → 输出找图需求单（仅 A 类）
3. 需要纹理：先用代码 `DotGrid`/`GlowOrb` 零素材方案；需图片纹理时人从图鱼素材选
4. 需要情境插画：先查 `插图库/`；为空或不匹配 → AI 用代码图标/几何/文字排版替代（B 类，不卡流程不等人）
5. **A/B 分类铁律**：A 类（背景图+封面图）本地没有 → 输出完整规格表人找图；B 类（插画/挂件/装饰）本地没有 → AI 用代码替代，**不输出找图需求**

> 用户也可**提前自搜囤图**（不必等找图需求单）：按 §4.5 找图指引的关键词与红线找，发 AI 验证合格后入库。原则：按缺口色系找、每色系 1-2 张够用，不批量囤。

**路径引入机制**：素材从根目录**复制**（非符号链接）到 `video/public/` 对应子目录：
```
背景素材/抽象模板/冷色系/BG-ABS-002.png → video/public/backgrounds/gXX/bg.jpg
```
命名规则：`gXX-s{屏号}-{角色}.{ext}`（如 g03-s1-bg.jpg）。音频按视频 ID 分子目录 `public/audio/{视频ID}/`，raw/ 放 TTS 原始输出。

### 4.2 图片使用规范（Remotion 中）

- 图片必须有入场动画（FadeInUp/ScaleIn/WipeIn 等），禁止裸放
- 背景图必须有叠加层保证文字可读（对比度 ≥4.5:1）
- 路径用 `staticFile()` 引用，禁止硬编码绝对路径
- 三类素材对应三个 public 子目录：backgrounds/ / textures/ / illustrations/
- data 文件通过 `image?: string` 字段指定图片路径

**背景图提供时机（优先级从高到低）**：
1. **用户已有背景图 → 设计稿前提供（最优）**：AI 设计时基于真实背景的明暗/色调/留白做配色与布局，一次到位。设计稿中必须标注背景明暗（浅色底 → 各屏设 `darkText: true`）与主色，预判前景适配
2. **无背景图 → 设计稿后按找图需求单**：AI 出需求单（含「前景兼容约束」字段，§4.3），用户按标准找图
3. **无论何时提供，still 验证不可省**——教训：设计稿阶段明知背景是浅色仍写了白字，靠 still 验证才发现对比度问题（darkText 适配）

**背景图显示策略（定调）**：
- **默认直接显示原图（blur=0）**——背景图按找图需求单选回后，本身就是"氛围好、内容区留白"的图，直接透出，不做毛玻璃模糊
- 仅当背景图过亮/过花、与前景对比度不足时，才用 `AccentOverlay` 主色调和（palette 主色 soft-light 18%，已有组件）做统一
- 毛玻璃模糊（blur 2-6px）降为**可选**，不作为默认（实测：纯色差、毛玻璃差，直接显示 + 约束前置才稳）
- 禁止全屏半透明遮罩（V-R07）

**背景图兼容验证（图到位后必做，防全量渲染后才发现撞色）**：
1. 背景图放入 `video/public/backgrounds/gXX/` 后，先渲染 1-2 帧 still（含前景元素的内容区帧）
2. 逐帧检查前景对比度：标题/正文/卡片与背景图同区域是否清晰（对比度 ≥4.5:1）、有无颜色重叠
3. 不达标 → 二选一：① 代码层局部处理（内容区局部暗化 / 文字加描边 / 卡片加白底）② 让用户换图或按「前景兼容约束」重新生成
4. 验证通过后才进入全量画面验证（关键帧渲染）

### 4.3 外部找图规格表（仅 A 类背景+封面）

```yaml
素材编号: IMG-GXX-01
来源: 外部找图
使用场景: S1 钩子屏全屏背景
画面位置: 全屏背景（文字在上层）
尺寸规格: 1080×1920 px，72dpi，JPG/PNG
风格方向: 抽象光斑/渐变色块/纹理（参照 spec/assets.json 已登记背景模板的风格描述）
色调要求: 与 palette 协调（写出主色 hex + 禁用色）
前景兼容约束: 内容区（y:200-1100）必须留白或低饱和；前景主色清单（如标题白字/卡片白底/强调色 #2E7D32），背景图同区域不得与之撞色；内容区禁高饱和色块/复杂纹理/人脸/文字
内容描述: 具体到元素+构图+留白（文字放哪里）
情绪氛围: 温暖/专业/科技…
检索关键词: 3-6 个（行业+风格+色调+元素）
AI生成描述: 平台无合适图时复制到 AI 生图工具（含画幅/主色值/核心元素/风格质感/行业氛围/留白/排除项/英文关键词/负面提示词）
版权要求: 可商用（站酷/创客贴/Envato/Unsplash License）
文件命名: g03-s1-bg.jpg
存放路径: video/public/backgrounds/g03/g03-s1-bg.jpg
```

> **背景图 AI 描述铁律**：只描述"质感+光色+氛围"，不描述具体物体（背景图是底色不是内容，画了咖啡杯会跟前景 UI 抢戏）。
> **前景兼容约束必填**：找图/生图需求必须包含「前景兼容约束」字段，否则图回来可能撞色返工。AI 生图提示词里同步写入：内容区留白、避开前景主色、无文字无 logo。

### 4.4 素材登记流程（入库=登记）

> 规则：**不登记不算入库**。新素材放入目录后必须在 `spec/assets.json` 登记一行，AI 才"知道"它、才能选用。
> 分级：A 级（背景图+封面模板）= 必登记、AI 必用；B 级（纹理/插画/挂件）= 按需登记，AI 有代码替代兜底；C 级（字体）= 登记即可；D 级（产品截图速查表）= 文章配图用，总数按 `截图素材/` 磁盘文件数计（含禁用项，禁用项在红线提示中标注）。

**登记流程**：
1. 新素材放入对应目录（背景素材/插图库/商用字体/截图素材）
2. 在 `spec/assets.json` 对应级别（A/B/C/D）登记：编号、名称、内容描述、路径、状态
3. 跑 `node scripts/check-facts.mjs` 验证登记路径与磁盘一致（A/B/C 级路径存在性 + D 级数量对账）
4. 背景图入库后，AI 设计稿即可按描述选用

**D 级截图使用规则**：写小红书/搜狐文章配图时**先查 `spec/assets.json` D 级**（80% 需求直接找到）；发布前必须裁剪微信元素（`spec/redlines.json` video_visual）。

### 4.5 找图指引（背景图缺口补取）

> 用户自搜囤图或 AI 出找图需求单时，按本指引的关键词与红线找。

**找图关键词**（按缺口色系）：
- 暖色系：抽象光斑 暖棕 奶油 柔和 竖版 无文字 高质感
- 冷色系：冰蓝 薄荷 柔光 渐变 竖版 留白 无文字
- 粉系：粉雾 渐变 网格 梦幻 柔和 竖版 无文字

**找图四红线**：
1. 内容区（y:200-1100）必须留白或低饱和，不得有高饱和色块/复杂纹理/人脸/文字
2. 与前景主色不撞色（标题白字/卡片白底/强调色）
3. 可商用授权（站酷/创客贴/Envato/Unsplash/Pexels）
4. 竖版 1080×1920，72dpi，JPG/PNG

**交付流程**：用户找到图 → 发 AI 验证（前景兼容 + 对比度）→ 合格入库登记 `spec/assets.json` → 设计稿选用。

## 5. 创作自由清单（哪些 AI 可自主决定）

> 以下全部交给 AI 自己决定，想怎么来怎么来，不用问、不用对齐。创造力来自多样性，条条框框太多，做出来的东西都一个样，反而不好。

### 5.1 完全自由的领域

| 领域 | 范围 | 说明 |
|---|---|---|
| **切入点** | 钩子怎么打、从哪个角度切入 | 可以是提问式、场景式、反常识式、数字式... 随便 |
| **叙事结构** | 几屏、顺序怎么排 | 8-10 屏为基准，可上下浮动，关键是内容深度够 6 个信息单元 |
| **句式和语气** | 书面语还是口语、严肃还是轻松 | 只要不违规，什么语气都行 |
| **画面设计** | 用什么组件、怎么排版、什么动效 | 代码 UI 组件随便组合，只要好看、信息清楚（画面审美标准见 `workflow/craft.md`） |
| **配色方案** | 主色、辅色、背景色 | 每个行业可以不一样，风格轮换 |
| **素材选择** | 用什么图、什么图标 | 只要合规、不侵权，随便选 |
| **具体例子** | 用什么行业场景举例 | 只要是该行业的真实场景，随便举 |
| **信息组织方式** | 列表式、对比式、流程式、故事式 | 怎么表达清楚怎么来 |

### 5.2 唯一的要求

**做完后对照以下 4 个自检问题问自己一遍**：

1. 看完老板会不会觉得"这个我店里也能用"？
2. 每个功能是不是都讲清了"在哪用、怎么用、用了有啥用"？
3. 我说的每一个"好"，有没有具体的东西支撑？
4. 剪掉一半会不会损失重要信息？

4 个都过了，就算好内容。

### 5.3 一句话总结

```
红线（spec/redlines.json 管）：不能错的，一条都不能碰
质量（本文件 §1.6 管）：要做好的，达到结果就行
创作自由（AI 管）：怎么达到，AI 自己说了算
```
